# 性能与调试（先测量，再动手）

---

## 一、铁律：**先测量，再优化**

没有测量数据的优化都是猜。**多数人的"优化"花在了根本不影响体验的地方**，同时把代码变复杂。

流程：**复现 → 量化（耗时/次数/内存）→ 二分（哪一半慢）→ 定位到单点 → 只改那一处 → 再量一次**。

## 二、常见瓶颈清单（按命中率排序）

| 瓶颈 | 表现 | 处理 |
|---|---|---|
| **N+1 查询** | 列表页慢，数据库调用次数随行数增长 | 批量查询/预加载 |
| **缺索引** | 数据量一涨就慢，本地小数据看不出来 | 给查询条件与排序字段加索引 |
| **串行外部调用** | 时间 = 各调用之和 | 能并行的并行；不能并行的改异步 |
| 全量加载 | 一次把几万行读进内存 | 分页/流式处理 |
| 重复计算 | 每次请求都重算同一结果 | 缓存或预计算 |
| 同步阻塞 | 单个慢任务卡住所有人 | 移到后台任务/队列 |
| 大对象拷贝/序列化 | CPU 高、内存涨 | 只取需要的字段 |
| 前端重渲染/资源过大 | 首屏慢、卡顿 | 按需加载、压缩、减少无谓状态更新 |

**判断顺序**：数据库 → 网络调用 → 序列化 → 计算 → 渲染。大多数"慢"在前两项。

## 三、缓存（用错比不用更糟）

- **什么时候用**：读多写少、计算贵、能接受短暂过期。
- **放哪层**：客户端 → CDN → 进程内 → 分布式缓存（越靠前越省事，越靠后越复杂）。
- **必须想清失效**：TTL、主动失效、版本号做键（`key:v3`）。
- **三个经典事故**：
  - 缓存穿透（查不存在的数据，每次打到数据库）→ 空值也缓存/布隆过滤器一类；
  - 缓存雪崩（大量键同时过期）→ 过期时间加随机抖动；
  - 缓存与真数据不一致（写完没失效）→ 明确"谁负责失效"。
- **绝不要把用户私有数据放进共享缓存**（越权泄漏的高发点）。

## 四、性能预算（要有数字）

| 指标 | 示例要求 |
|---|---|
| 首屏可交互 | 3 秒内（弱网可放宽） |
| 接口响应 | P95 < 500ms |
| 并发 | 支持 N 人同时使用（写清 N） |
| 内存/包体积 | 明确上限 |
| 成本/次调用 | API 或模型调用单次成本上限 |

**超预算就当成 bug**，而不是"以后优化"。

## 五、容量估算（提前算，不提前优化）

- 现在多少数据/用户？一年后多少？**增长 10 倍时哪一步先崩？**
- 估算表：数据行数 × 单行大小 = 存储；请求数 × 单请求成本 = 费用。
- 结论通常是"现在不用优化，但要在 X 处留好接口"——把它写进图纸的"以后再说"。

## 六、调试流程（比工具重要）

1. **先写最小可复现例子**（能稳定复现，才谈得上修）。偶发问题优先怀疑并发与时序。
2. **一次只改一个变量**，记录假设 → 验证 → 结论。
3. **二分定位**：注释/绕过一半流程，看问题在哪一半。
4. 别用"试试看"的方式连着改三处（改了也不知道是哪处生效）。
5. 修完补一条**回归测试**（见 `testing-strategy.md`），否则同一 bug 会回来。

## 七、可观测（出问题时你能看到什么）

- **日志**：结构化（时间、级别、请求 ID、模块、上下文）；级别用法——ERROR（要人处理）、WARN（可能有问题）、INFO（关键流程节点）、DEBUG（排查时开）。
- **关联 ID**：一个请求贯穿多模块/多服务，靠它串起来。
- **指标**：成功率、P95 延迟、错误数、队列积压、调用次数与费用。
- **告警**：无人值守必须有；告警要能定位而不是只喊"出错了"。

## 八、三条禁忌

1. 不测就优化。
2. 用"感觉"判断快慢（"我感觉是这个慢"）。
3. 为不存在的规模优化（还没有 100 个用户就上分库分表）。
