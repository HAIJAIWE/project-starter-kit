# 多语言（i18n）与无障碍（a11y）

**共同规律：第一天做很便宜，以后做很贵。** 但也不要默认全做——先看触发条件。

---

## 一、什么时候真需要（触发条件，不是默认需求）

| 需求 | 触发信号 |
|---|---|
| **i18n 多语言** | 有非母语使用者；要上架应用商店到多语言地区；企业/政府客户要求；产品要卖到国外 |
| **文案抽取（即使只有一种语言）** | **任何有界面的项目都建议做**——见下方"最小做法"，成本极低 |
| **a11y 无障碍** | 面向公众；上架商店；企业采购要求；用户里有老人/视障用户；很多地区的法规引用 WCAG |

**不要为了"以后可能国际化"就上完整翻译流程**（多语言文件 + 翻译平台 + 测试矩阵）。但"别把文案硬编码在逻辑里"这件事，**第一天就该做**。

---

## 二、i18n 最小做法（成本低，收益立刻）

1. **文案集中存放**：所有给用户看的字串放进一个地方（按模块命名空间），不要散落在代码里。
   - 好处不只是翻译：改文案不用翻代码；能一眼看出哪些文案没人用。
2. **不拼句子**：`"你好，" + 名字 + "，你有" + n + "条提醒"` 在别的语言会碎掉。
   用**带占位符的完整句子**（`{name}`、`{count}`），让译文能重排语序。
3. **复数与量词走规则**：别写 `count == 1 ? "条" : "条"`；不同语言的复数规则不一样，用标准库的复数支持。
4. **日期/时间/数字/货币用标准格式化 API**，别手工拼 `YYYY/MM/DD`（顺序、分隔符、历法都可能不同）。
5. **时间存 UTC、展示本地时区**；"今天"的边界按**用户时区**算（这是跨时区最容易错的地方）。
6. **金额**：整数最小单位存储（见 `data-and-quality.md`），展示时再按货币格式化。
7. **别写死布局宽度**：德语常比英语长 30%+，中文更短；按钮和标签要能自适应或截断有提示。
8. **排序与搜索**：不同语言的字母顺序与大小写规则不同（尤其土耳其语、德语的 ß），用标准库的区域感知比较。
9. **从右到左（RTL）**：若支持阿拉伯语/希伯来语，布局要能镜像——**这是"第一天不做、以后极贵"的典型**，前期只需避免写死 `left/right`。
10. **缺翻译的降级**：回退到默认语言并**记录缺失**（别显示空白或键名）。

### i18n 常见坑
| 坑 | 后果 |
|---|---|
| 文案硬编码在逻辑与测试里 | 后期改造要动所有文件和所有测试 |
| 拼接句子 | 译文语序错乱 |
| 用图标/颜色单独表意 | 跨文化歧义（见 a11y 同样问题） |
| 假设"一周从周一开始" | 部分地区周日开始 |
| 输入校验只认 ASCII | 姓名、地址、电话格式千差万别（别用正则卡死姓名） |

## 三、无障碍（a11y）最小清单

面向公众的产品，至少做到 **WCAG 的 A/AA 级基本项**（依据：[W3C WCAG](https://www.w3.org/WAI/standards-guidelines/wcag/)，很多地区法规引用它）：

- [ ] **键盘可达**：只用 Tab/Enter/Esc 能完成主要操作；焦点顺序合理；**焦点可见**（别把 outline 去掉）。
- [ ] **语义正确**：按钮就是按钮（别用 div 假装）；标题用标题标签；列表用列表标签。
- [ ] **表单**：每个输入有真正的 label（**别用 placeholder 当 label**）；错误提示与对应输入关联，并说明怎么改。
- [ ] **图片**：有意义的图给替代文字；纯装饰图标记为装饰。
- [ ] **对比度**：正文 ≥ 4.5:1；**不要只靠颜色传达信息**（"红色=错误"要配文字或图标）。
- [ ] **可放大**：字号放大到 200% 不破版、不丢内容。
- [ ] **动效可关**：尊重"减少动态效果"的系统设置；不用自动播放的音视频。
- [ ] **超时与自动刷新**：有超时要能延长；别让内容自动变化打断操作。

### 怎么测（不用专业工具也能测）
1. 拔掉鼠标，只用键盘走一遍主流程。
2. 屏幕阅读器抽测一次（系统自带即可）。
3. 对比度工具扫一遍主要配色。
4. 系统字号放大到 200% 再看一遍。

### a11y 常见坑
| 坑 | 后果 |
|---|---|
| `div` 当按钮、`a` 当按钮 | 键盘和读屏都用不了 |
| 去掉焦点框 | 键盘用户迷路 |
| 只靠颜色/图标 | 色盲与读屏用户收不到信息 |
| 弹窗不锁焦点 | 读屏在背后乱跳 |
| 表单错误只红框不写字 | 不知道错在哪 |

## 四、两者对架构的实际影响

| 影响 | 说明 |
|---|---|
| 文案层独立 | 界面模块下多一个"文案"模块；**不进业务层** |
| 时区进入数据模型 | 存 UTC + 记录用户时区（见 `data-and-quality.md`） |
| 布局约束 | 不能写死宽度与方向（RTL 就靠这个） |
| 测试成本 | 多语言要测长文案与 RTL；a11y 要加键盘走查（可并入关键场景走查） |
| 交付清单 | 上架商店/企业采购前，这两项会被明确要求 |

## 五、纪律

1. **文案不硬编码**：从第一天做，成本几乎为零。
2. **不为了"可能国际化"上完整体系**：触发条件出现再上翻译流程。
3. **a11y 与 i18n 都必须进"关键场景走查"**，否则永远不会被检查。
