# 各类项目怎么切子系统

**候选不是答案。** 照抄清单 = 没做架构。拿到候选后按实际情况增删，并让用户确认边界。

> **关于「规模适配」**：这不是"砍功能"，而是专业上的**按规模裁剪深度**——同一套方法，按项目规模决定先做哪些子系统、产出物写多深。
> **裁剪的只有范围，不是标准**：接口契约、密钥分离、能回滚、README、一条真测试，任何规模都不许省。
> 判断依据不是"项目小所以少做"，而是"这个子系统在这规模下必须先做吗"。

## 一、五种问法 → 现推子系统（没有对应类型时用这个）

| 问用户 | 推出哪类子系统 |
|---|---|
| 用户看到什么？点了什么？从哪进来？ | **界面 / 接入子系统**（网页、聊天窗口、命令行、定时触发） |
| 这东西替谁做什么判断、走什么流程？ | **业务子系统**（核心规则，最该被单独测试） |
| 数据从哪来？存哪？留多久？给谁看？ | **数据子系统**（读写、存储、备份、报表） |
| 要跟哪些外部东西打交道？ | **集成子系统**（平台接口、支付、地图、大模型、别人的系统） |
| 出错了谁发现？有没有定时任务？要不要部署？ | **运维 / 调度子系统**（日志、监控、定时、配置） |

绝大多数产品就是这五类的子集。**少于 2 类说明项目太小，别硬拆**；多于 7 类说明拆太碎。

## 二、按项目类型的候选清单（14 类）

| 项目类型 | 子系统候选 | 规模适配（缩范围，不降标准） | 专属坑 / 合规红线 |
|---|---|---|---|
| **网站 / Web 应用** | 前端界面、后端接口、数据存储、用户与权限、后台管理 | 前后端同仓库，权限用现成机制 | SEO 与首屏（要不要服务端渲染得早定）；表单重复提交；跨域与 Cookie 策略；图片/带宽成本 |
| **后端 API / SaaS** | 接入层（路由鉴权限流）、业务、数据访问、任务队列、第三方集成、运维监控 | 队列先同步调用，监控先用日志 | 版本兼容（老客户端还在调）；幂等（重试会重复下单）；限流与配额；错误码要稳定 |
| **移动 App / 小程序** | 界面导航、状态管理、网络请求、本地存储、推送、原生能力桥 | 状态放页面内，砍推送与原生桥 | 上架审核周期与规则；签名证书丢失=无法更新；离线与弱网；包体积；隐私政策与权限弹窗（合规硬要求） |
| **桌面应用** | 界面、核心逻辑、本地文件/数据库、自动更新 | 不做自动更新，手动覆盖 | 代码签名（否则系统报警）；跨平台差异；用户本地数据升级迁移 |
| **命令行工具 / 脚本** | 命令与参数解析、核心逻辑、配置读取、输出与退出码 | 子系统就是 1 个，模块=函数分组 | 退出码约定（脚本要靠它判断成败）；跨平台路径；破坏性操作要二次确认；标准输入输出被管道化时别打印花活 |
| **聊天机器人 / IM 机器人（各类 IM 平台）** | 平台接入适配、消息路由分发、指令与业务处理、AI 能力、数据存储、定时任务、权限与黑名单 | 砍定时与权限，指令用前缀判断 | **平台风控/封号**（别高频群发）；消息会重复投递 → 必须幂等；平台协议变更会打断服务；用户消息可能含隐私，转发给大模型前要想清楚；平台接入单独成模块，别混进业务 |
| **AI / 智能体应用** | 智能体编排、模型接入、工具与集成、记忆与知识库、数据、界面、评测 | 砍记忆库与评测；单智能体 + 少量工具；模型接入抽成接口 | **token 成本与限流**（要预算上限与降级）；幻觉无兜底；提示词散落无法维护；把用户隐私数据发给第三方模型（合规）；评测缺失导致"改了不知道好坏"；工具调用要鉴权与沙箱 |
| **数据管道 / 爬虫 / 报表** | 采集、清洗标准化、存储、分析统计、展示导出、调度 | 砍调度（手动跑）；采集与清洗分开 | 遵守目标站条款与 robots、别越界抓取；请求频率与礼貌延迟；数据去重与增量；源站改版会静默失败（要能发现）；数据留存期限 |
| **浏览器插件** | 后台脚本、内容脚本、弹窗界面、存储、页面与后台通信 | 只做内容脚本 + 存储 | 商店审核与最小权限原则（权限要得越多越难过审）；页面改版就会失效；跨域限制；别注入影响宿主页面的全局变量 |
| **游戏** | 主循环、实体与场景、资源加载、输入、存档、关卡数据 | 砍存档与资源管线 | 帧率与内存预算（先定预算再写）；存档版本兼容；资源版权；不同设备性能差异 |
| **内部自动化工具** | 触发器、业务规则、系统对接、通知、日志与重试 | 触发器用定时任务；先不做重试 | 权限与审计（谁能改规则）；对接系统变更无通知；静默失败 → 必须有失败告警；含公司数据的日志别乱发 |
| **库 / SDK / 组件包** | 公开接口层、核心实现、适配器、文档与示例 | 子系统=公开接口 + 实现两层 | **语义化版本与破坏性变更策略**（改别人会崩）；类型/文档与实现不同步；依赖越少越好；示例代码要能真的跑 |
| **硬件 / IoT** | 设备端固件、通信协议、服务端、控制界面、数据存储 | 砍控制界面，先用命令行发指令 | 断网与重连；固件升级失败会变砖（要回滚方案）；设备时钟不准；弱设备内存/电量限制 |
| **电商 / 内容站** | 前台展示、内容/商品管理、订单交易、支付、库存、后台运营 | 砍支付与库存（手工处理），先跑通下单 | **金额精度**（别用浮点，用整数最小单位）；对账与退款流程；库存超卖（并发）；发票与合规；支付回调必须验签 + 幂等 |

## 二·补 · 部署形态 → 子系统切法（先定这个，再谈拆包）

| 部署形态 | 典型切法 | 别做 |
|---|---|---|
| 单机脚本 / 本地工具 | 1 个包，内部按模块分目录 | 别拆前后端，别建多包 |
| 桌面 / 移动 App | 客户端包 + （可选）后端包 | 别把后端逻辑塞进客户端（密钥会泄漏） |
| 网站（前后端分离） | 前端子系统 + 后端子系统 + 共享契约（类型/接口定义） | 别让前端直接连数据库；共享契约要单独一层，不是复制粘贴 |
| 单体服务 + 定时任务 | 一个服务 + 任务模块（同一份代码两种入口） | 别为定时任务单独起一个服务 |
| 无服务器 / 云函数 | 按触发器分函数，共享业务逻辑抽成库 | 别把有状态的东西放函数内存里 |
| 多服务 | 每个服务 = 一个子系统，服务间只走接口/事件 | 别在没有运维能力时上；服务间共享数据库会立刻退化成分布式单体 |

## 三、没有特殊理由时的默认技术栈（**用户有偏好就听用户的**）

| 项目类型 | 默认起点 | 说明 |
|---|---|---|
| 网站 / 后台管理 | 前端框架（自带路由与构建）+ 一个后端框架 | 别手写打包配置 |
| 后端 API | 主流语言的原生 Web 框架 | 先单体，别上微服务 |
| CLI | 该语言的成熟参数解析库 | 别手写参数解析 |
| 聊天机器人 | 平台官方 SDK/适配库 + 一个机器人框架 | 平台协议自己实现极易被封 |
| AI / 智能体 | 一个主流智能体框架 + 官方模型 SDK | 模型调用必须包在自己的接口后，方便换供应商 |
| 爬虫 | 成熟 HTTP 客户端 + HTML 解析库 | 优先找官方 API，别一上来就爬页面 |
| 数据/报表 | 该语言的表格与数据处理库 | 先把数据落到本地文件/库，再接可视化 |
| 通用数据库 | 关系型数据库（除非明确是文档/键值/时序场景） | 小项目用 SQLite/Postgres 起步足够 |

**规则**：栈要选"出问题能搜到答案"的，不要选"看起来很酷"的；**版本号必须真实存在**，写进 README 前先在官方源确认。

## 四、切完自检

- [ ] 每个子系统都能回答"单独替换？单独测试？"
- [ ] 每个子系统写了"不做什么"
- [ ] 没有"其他 / 杂项 / 工具"这类兜底子系统
- [ ] 用户能用自己的话复述出这几个子系统（复述不出来 = 切错了）
- [ ] 子系统数量在 2–7 之间，不凑数
- [ ] 该类型表格第三列的"专属坑"，至少逐条确认过一次
