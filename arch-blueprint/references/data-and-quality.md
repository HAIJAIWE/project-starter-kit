# 数据模型与质量属性（分层之外必须画的三样之二三）

只画五层线不画这两样，图纸一定是错的——因为它们**反过来决定子系统边界**。

---

# 第一部分：数据模型

## 一、必须回答的问题

| 问题 | 为什么必须答 | 答不出会怎样 |
|---|---|---|
| 有哪些"东西"（实体）？ | 实体就是业务语言里的名词 | 表和业务对不上，字段越加越乱 |
| 每个实体谁写、谁只读？ | **写权限归属 = 子系统边界** | 两个子系统共写一张表，边界是假的 |
| 一个实体活多久？什么时候删？ | 涉及留存期限与合规 | 三年后数据没人敢删 |
| 删除是软删还是硬删？ | 影响查询、审计、恢复 | 用户"删了"却还能被查到 |
| 数据量级与增长速度？ | 决定要不要索引/归档/分表 | 到十万行才发现慢 |
| 有没有备份？恢复演练过吗？ | 唯一能救命的东西 | 丢数据就是丢用户 |

## 二、最小做法（不要求画专业 ER 图）

画一张表就够：

| 实体 | 关键字段 | 谁写（哪个子系统） | 谁读 | 生命周期 | 备注 |
|---|---|---|---|---|---|
| 用户 | id、昵称、创建时间 | 用户子系统 | 业务、后台 | 注销后 30 天删除 | 手机号属个人信息，最小化收集 |
| 消息记录 | id、来源、内容、时间 | 接入子系统 | 业务、统计 | 保留 90 天 | 内容可能含隐私，转发第三方前需确认 |

## 三、判定边界的一招

> **一张表如果被两个子系统写，说明子系统切错了。**

要么把两个子系统合并，要么把写权限收归一个子系统，另一个只通过接口读。

## 四、常见数据坑

| 坑 | 怎么做 |
|---|---|
| 金额用浮点数 | 用整数最小单位（分/厘）或十进制类型——**永远不要用浮点存钱** |
| 时间不带时区 | 存 UTC，展示时再转本地；别存"本地时间字符串" |
| 主键用什么 | 对外可见的 ID 用随机 ID（避免自增暴露业务量） |
| 并发写覆盖 | 加版本号/时间戳做乐观锁，或行级锁；先问"两个人同时改会怎样" |
| 重复提交 | 关键写操作要幂等键（防双击、防重试重复下单） |
| 手动改生产库 | 一律走迁移脚本（见 `engineering-baseline.md`） |
| 数字精度与长度 | 字段长度/精度按最坏情况定，事后改结构很贵 |

# 第二部分：质量属性（非功能需求）

**架构不是被功能决定的，是被质量属性决定的。** 同一堆功能，要求"10 个人用"和"10 万人用"，架构完全不同。
白话版分类（分类框架可参照 ISO/IEC 25010）：

| 属性 | 要问用户的话 | 它的架构后果 |
|---|---|---|
| **性能 / 容量** | 多少人用？峰值多少？多快算能接受？ | 要不要缓存、索引、队列、异步；要不要读写分离 |
| **可用性** | 挂掉能接受多久？谁能重启？ | 要不要多实例、健康检查、自动重启、降级方案 |
| **安全** | 谁能看？谁能改？数据敏感吗？ | 要不要鉴权层、权限模型、密钥管理、审计日志 |
| **隐私与合规** | 收集了谁的什么数据？能不能发给第三方（含大模型）？ | 数据最小化、脱敏、留存期限、用户删除权 |
| **成本** | 每月最多花多少钱？（云 + 模型 + 短信/带宽） | 要不要批处理、缓存、小模型、限流；预算上限与降级策略 |
| **可维护性** | 三个月后谁改？他自己看得懂吗？ | 决定抽象程度与文档量——**无人接手就别过度抽象** |
| **可移植性** | 会不会换平台/换供应商/换数据库？ | 决定要不要在外部依赖前加一层接口（端口适配器） |
| **可访问性 / 体验** | 谁用？什么设备？网络差吗？弱网要能用吗？ | 离线优先、包体积、字体与对比度、操作步数 |
| **可观测性** | 出问题你怎么知道？ | 日志、指标、告警；无人值守时必须主动告警 |

## 质量属性 → 架构动作（对照表）

| 用户说 | 别急着上 | 先做 |
|---|---|---|
| "以后用户会很多" | 微服务、分库分表 | 加索引、把慢查询找出来、留好接口边界 |
| "要快" | 缓存全上 | 先测：到底哪一步慢（大部分是数据库或串行调用） |
| "不能丢数据" | 复杂高可用 | 备份 + 恢复演练 + 关键写操作幂等 |
| "要能换模型/换供应商" | 到处写适配器 | 只把**外部调用**抽成接口，内部别抽 |
| "预算有限" | 全用最强模型 | 分级调用（简单任务用便宜模型）+ 缓存 + 预算上限与降级 |
| "怕出事" | 什么都加 | 先做：密钥分离、权限校验、失败告警 |

## 三、三条硬规矩

1. **质量属性要写数字**："快"不是要求，"首屏 2 秒内、100 人同时用"才是。
2. **写不出数字就先写假设**，并在图纸「待确认」里标注——假设错了要能回头改。
3. **超出预算的质量属性一律不做**：一个人维护的项目追求 99.99% 可用性，是把命交给运气。

# 第三部分：上线才发现清单（逐条过一遍，成本极低）

- [ ] 时区与夏令时（服务器时间是 UTC 还是本地？）
- [ ] 金额精度与四舍五入规则
- [ ] 两个人同时改同一条数据会怎样
- [ ] 用户连点两次提交按钮会怎样
- [ ] 第三方接口超时/限流/返回错误时的表现
- [ ] 第三方接口改版导致静默失败怎么发现
- [ ] 数据库连不上时前端显示什么
- [ ] 大文件上传/下载中断能否续传
- [ ] 日志里会不会出现密钥、手机号、身份证
- [ ] 备份到底能不能恢复（演练过没有）
- [ ] 密钥泄露了怎么吊销、多久能生效
- [ ] 陌生人拿到链接能不能访问别人的数据（越权）
- [ ] 删除数据后是否真的不可访问
- [ ] 升级失败能不能回滚到上一版
