# 测试策略（测什么、不测什么、怎么测）

**测试的目的不是覆盖率，是"敢改"。** 改一行代码不心虚，才算有测试。
本技能里的测试只有两个用法：① 接口先行时验证契约；② 让后续每次改动都能被验证。

---

## 一、测什么、不测什么

| 对象 | 测吗 | 理由 |
|---|---|---|
| 业务规则（算钱、判权限、状态流转） | **必测** | 错了就是真错，且逻辑会不断改 |
| 接口契约（输入/输出/错误） | **必测** | 假实现 + 契约测试能挡住大部分返工 |
| 数据读写（真数据库/真文件） | 测（集成） | 最容易在环境差异上翻车 |
| 第三方 API | **不测**（造假对象） | 你控制不了对方；但要测"对方失败时你的反应" |
| 框架/标准库 | 不测 | 那是别人的责任 |
| UI 布局细节 | 少测 | 脆、收益低；用关键场景人工走查 |
| 纯格式化/纯转发函数 | 不测 | 没有逻辑就没有价值 |

## 二、测试金字塔（Mike Cohn）

```
        /\        端到端（少）：能跑通第一条关键场景就够
       /  \
      /____\      集成（适量）：模块之间、真数据库
     /      \
    /________\    单元（多）：业务规则，毫秒级，改一次跑一次
```

**反模式：冰淇淋甜筒**——大量端到端、少量单元。结果：跑一次十分钟、经常假失败（flaky）、没人愿意跑，最后全部被忽略。

## 三、假对象怎么选（从好到差）

| 类型 | 说明 | 什么时候用 |
|---|---|---|
| **真实实现** | 真数据库、真临时目录、内存版服务 | **优先**——最不容易骗自己 |
| **Fake（假实现）** | 有真实行为的最简实现（内存仓库） | 接口先行阶段的默认选择 |
| **Stub（桩）** | 返回固定值 | 只需要"能返回"时 |
| **Mock（模拟）** | 断言"被调用了几次、按什么顺序" | 只在验证"副作用"时用 |

**判断信号**：一个测试里 mock 超过两三个，通常说明设计耦合太重——该抽接口，而不是继续 mock。

## 四、写测试的规矩

- 一个测试只断言一件事；名字描述行为：`下单时库存不足则失败`。
- 每个测试独立、可并行、不依赖执行顺序；测试之间不共享可变状态。
- 测试数据用工厂函数/夹具生成，别复制粘贴一坨 JSON。
- **一个测试必须能失败**：写完把它对应的实现改坏一处，看它是否变红（防"恒真断言"）。
- 修好的 bug 必须补一条测试（防复发）——这是性价比最高的一条。
- 慢测试要修，不是忽略（慢 → 不跑 → 等于没有）。

## 五、覆盖率怎么用

- 用来**发现"完全没测的地方"**，不是达标指标（"覆盖率 80%" 可以全是空测）。
- 别为了让覆盖率好看去测 getter/setter。
- 关键业务规则的覆盖要人工看一遍，别交给工具判断。

## 六、外部依赖怎么测

| 依赖 | 办法 |
|---|---|
| 数据库 | 本地真库（容器/临时文件）+ 每个测试独立 schema 或事务回滚 |
| 第三方 HTTP | 先包成自己的接口 → 测试时给假实现；必要时录播真实响应 |
| 大模型 | 包成接口 → 假实现返回固定文本；另建**小评测集**验证提示词改动（见 `patterns.md`） |
| 时间/随机数 | 注入时钟与随机源，否则测试不可重复 |
| 文件系统 | 临时目录，别用固定路径 |

## 七、不能自动化的部分

- 写**关键场景走查清单**（点一遍、发一条消息、跑一条命令），发布前手动跑。
- 覆盖不到的场景就是**现在不做**的功能（与 `roadmap.md` 阶段 0 一致）。

## 八、什么时候写

1. **接口阶段先写假实现**，让调用方能跑通——这一步的"测试"是调用方。
2. **业务逻辑**：至少与实现同步写；能先写就先写。
3. **修 bug**：先写能复现的测试，再修（否则不知道修没修好）。
4. **重构前**：没有测试就先补上要改的那部分（这是重写的护网，见 `release-and-evolution.md`）。

## 九、最小落地顺序（别一上来追求完备）

```
1. 业务规则单元测试（3–5 条核心规则）
2. 接口契约测试（假实现能跑通调用方）
3. 一条端到端：第一条关键场景自动跑
4. 修 bug 补回归测试（持续）
5. 集成测试（真数据库读写）
6. CI 里自动跑（否则等于没有）
```
