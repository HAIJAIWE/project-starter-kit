# 模式库：四类图纸 + 权威出处

**使用原则：先匹配触发条件，再选模式；触发条件不满足就不选。** 每个模式都写了代价——代价不能承受时宁可不用。
一次最多选 2 个模式。

---

## 一、架构风格（整个项目的骨架）

| 模式 | 长什么样 | 触发条件（满足才用） | 代价 | 出处 |
|---|---|---|---|---|
| **分层 Layered** | 界面 → 业务 → 数据访问，每层只跟相邻层说话 | **绝大多数项目的默认起点** | 严格 vs 宽松分层（上层能否跳级）必须提前写进图纸，否则变成"哪里方便调哪里" | 通用分层设计；依赖规则见 Clean Architecture |
| **MVC / MVVM** | 把"输入→状态→渲染"分成三块，框架通常自带 | 有界面的项目（桌面、前端、移动）默认就用 | 简单页面会被模板代码淹没；别把业务逻辑写进 Controller/ViewModel | 通用 GUI 模式（各框架文档为一手出处） |
| **模块化单体（Modular Monolith）** | 一个可部署单元，内部按业务划出强边界模块 | **小团队做中大型系统的推荐默认**：想要微服务的边界，但不想付分布式代价 | 边界靠纪律维持，需要自动化校验（import-linter / ArchUnit） | 业界共识（Fowler *MonolithFirst* 等） |
| **垂直切片 Vertical Slice** | 按业务切：一个功能自带界面+逻辑+存储 | 业务线多，且改一个功能要动 4 个以上技术分层目录 | 需要约定，否则共享逻辑被复制多份。**不等于微服务** | Jimmy Bogard |
| **六边形 / 端口适配器** | 核心逻辑只认"端口"，外部系统都做成"适配器" | 要接多个外部实现（多种数据库、平台、大模型） | 多一层抽象；小项目纯属绕 | Alistair Cockburn |
| **BFF（Backend for Frontend）** | 每种前端配一个自己的后端聚合层 | 多端（Web + App + 小程序）需求差异大 | 多一层要维护；端少时是负担 | 通用（Sam Newman 等） |
| **事件驱动 EDA** | 不直接调用，改发布/订阅事件 | 有多个消费者响应同一件事，或要削峰、跨系统解耦 | **最终一致**；链路难调试；必须补幂等 + outbox；本地事务失效 | AWS / Azure 架构中心 |
| **CQRS** | 读模型和写模型彻底分开 | 读写负载或数据模型差异极大，且已到性能瓶颈 | 复杂度显著上升；通常伴随最终一致 | Greg Young / Martin Fowler |
| **微内核 / 插件化** | 核心极小，能力做成插件注册 | 要给别人扩展，或功能按需装载 | 需要稳定的插件契约与生命周期 | 通用（编辑器、构建工具常用） |
| **无服务器 / 云函数** | 按触发器拆函数，按调用付费 | 流量峰谷极大、事件驱动、不想管服务器 | 冷启动、超时限制、本地调试难、有状态东西不能放内存 | 各云厂商官方文档 |
| **微服务** | 按业务拆成独立部署的服务 | 多团队独立发布扩容，且已具备分布式运维能力 | 分布式复杂度爆炸：网络、事务、追踪、部署 | 通用；小团队慎入 |

**默认路径**：模块化单体 + 分层 → 业务变多时用垂直切片重排 → 真需要独立扩展/多团队时才谈微服务。
**参照系**：ThoughtWorks 技术雷达多年把微服务放在 Adopt 环之外（[InfoQ 报道](https://www.infoq.com/news/2018/06/microservices-adopt-radar/)），Martin Fowler 也主张 *MonolithFirst*。别把微服务当"先进"。

## 二、模块之间怎么通话（选型表）

| 方式 | 什么时候选 | 代价 |
|---|---|---|
| **同进程直接调用**（默认） | 同一个程序内部 | 耦合较高，所以要经过接口 |
| **REST / HTTP 接口** | 前后端分离、给第三方调用 | 需要定义版本、错误码、鉴权 |
| **GraphQL** | 前端要灵活取数据、字段组合多变 | 服务端复杂度上升，缓存与限流更难 |
| **WebSocket / SSE** | 服务器要主动推（聊天、实时看板、进度） | 连接状态管理、断线重连要自己写 |
| **消息队列** | 要削峰、要重试、要多个消费者 | 运维成本 + 最终一致 + 消息顺序问题 |
| **共享数据库 / 文件** | 临时过渡、批处理 | 强耦合，改表结构连锁崩；只适合过渡 |
| **定时轮询** | 对方只有查询接口、实时性要求低 | 有延迟、浪费请求；必须处理重复执行 |
| **Webhook 回调** | 第三方有事通知你（支付、GitHub） | 要验签、要幂等、要处理重复投递 |

**默认路径**：同进程直接调用 → 跨进程才上 REST → 要实时才上 WebSocket → 要解耦/削峰才上队列。

## 三、代码组织

| 模式 | 什么时候选 | 代价 |
|---|---|---|
| **单体分层 Monolithic Layered** | 中小项目默认起点 | 业务一多容易"按技术切碎、业务散落" |
| **垂直切片 Vertical Slice** | 业务线多、希望改一个功能只动一个文件夹 | 需要约定，否则共享逻辑被复制 |
| **Monorepo（单仓库多包）** | 有多个需要独立发布的包，且要共享代码 | 工具链成本：包管理器工作区、构建编排、CI 复杂度 |

**经验线**：包少于 3 个、且不需要独立部署时，不要上 monorepo。

## 四、智能体协作模式（**只有做 AI / 智能体项目才看这节**）

普通项目直接跳过——**别给记账网站安排多智能体**。

| 模式 | 长什么样 | 触发条件 | 代价 | 出处 |
|---|---|---|---|---|
| **顺序 Sequential** | 流水线：A 做完交给 B | 步骤固定、有明确先后 | 慢；任一步失败后面全废 | Microsoft（AutoGen 系） |
| **并发 Concurrent** | 广播：同一任务发给多个智能体各自处理 | 子任务互不依赖、要快 | 必须额外写汇总与去重 | Microsoft（AutoGen 系） |
| **群聊 Group Chat** | 圆桌会议，主持人控制发言顺序 | 需要多视角讨论且结论要收敛 | 容易跑题；token 成本高 | Microsoft（AutoGen 系） |
| **移交 Handoff** | 接力棒：控制权整段交给下一个专家 | 角色分明、一问一答转专家 | 容易互相踢皮球，必须写兜底 | OpenAI Swarm / Agents SDK、Semantic Kernel |
| **磁性编排 Magentic** | 管理者只维护任务账本（ledger）动态规划并指挥专业智能体 | 开放型复杂任务，事先不知道要几步 | 最贵、最难调、结果难预测 | Microsoft Magentic-One |

**命名纠正**：是 **Magentic**（源自 Microsoft 的 Magentic-One），不是 "Magnetic"。中文"磁性编排"是意译，写代码/查文档时用 `Magentic`。

**优先级提醒**：官方文档普遍强调——任务简单就先把**单智能体 + 工具**做好；团队编排是能力不够时的解法，不是起点。

**AI 项目额外必须有的四件**（缺一件都会在两周后崩）：

1. **模型接入抽成接口** —— 换模型/换供应商不改业务代码，也方便降级到便宜模型。
2. **提示词独立成模块** —— 集中版本管理，不能散落在业务代码里。
3. **工具契约与实现分离** —— 名字/参数/说明（给模型看）≠ 执行实现（给人看）。
4. **评测与日志** —— 没有评测集，改了提示词或换了模型就不知道是变好还是变坏。

## 五、权威出处（要对照就看这些，别拿小众包当标准）

| 类别 | 出处 | 用来解决什么 |
|---|---|---|
| 架构文档怎么写 | **arc42**（模板化架构文档）、**C4 model**（层次图规范） | 图纸该有哪些章节、怎么画层次 |
| 决策怎么留痕 | **ADR / Architecture Decision Record**（Michael Nygard 提出） | 记录"为什么这么选"，防后人反复推翻 |
| 工程约定 | **12-Factor App** | 配置、日志、环境、进程模型 |
| 质量属性分类 | **ISO/IEC 25010** | 性能、可靠性、安全性、可维护性怎么列全 |
| 安全 | **OWASP ASVS**（应用安全验证标准）、**OWASP Securing Agentic Applications**（智能体应用安全） | 鉴权、密钥、注入、智能体工具调用的安全要求 |
| 架构原则 | **Clean Architecture**（依赖规则、SDP）、**DDD**（限界上下文） | 依赖方向、子系统边界 |
| 技术选型参照 | **ThoughtWorks Technology Radar** | 某个技术处在"试验/评估/暂缓"哪一档 |
| 智能体主流框架 | **Microsoft Agent Framework**（AutoGen 与 Semantic Kernel 的继承者）、**LangGraph**、**CrewAI**、**OpenAI Agents SDK**、**Vercel AI SDK** | 只用来对照"别人怎么组织模块"，**不照抄目录** |

**关于上一版引用的 `axl-sdk/axl`、`tinyagent-ts`、`node-agent`：已从参考清单移除。** 它们确实存在于 npm/GitHub，但都是使用面很窄的第三方包，拿它们当范例等于把"某一个人的一次选择"包装成行业标准——这是不专业的。五层线与依赖铁律的支撑来自上表的标准与经典文献，不依赖任何具体项目。

**引用纪律**：

1. 优先引用标准、官方文档、经典文献；具体项目只作对照，且必须说明"这是某一家的做法"。
2. 不写具体 star 数、下载量、"最流行"这类无法当场核实的说法。
3. 版本号必须在官方源真实存在；不确定就写"以官方最新文档为准"。
