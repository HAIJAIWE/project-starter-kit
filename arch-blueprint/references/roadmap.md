# 八阶段详解：动作、产出物、出口标准、常见错误

主线顺序：**立项 → 技术线 → 架构 → 契约 → 工程化 → 实现 → 交付 → 演进**
可以回退，不许跳。每个阶段的产出物都要落成文件（`docs/` 下），只在聊天里说 = 下个会话的 AI 又不知道。

---

## 阶段 0 · 立项与边界

**目标**：把"我有个想法"变成"这次具体做什么、做到哪为止"。

**动作**
1. 问清五个问题：给谁用？帮他完成哪个动作？他从哪里用上？数据从哪来给谁看？跑在哪谁维护？
2. 让用户用大白话讲 **3–5 个关键场景**（他会怎么用它）。
3. 把场景标上"这次做 / 以后再说"。**第一条场景就是 MVP 边界。**
4. 明确列出"不做清单"。

**产出物**：项目一句话说明、关键场景表、MVP 边界、不做清单（写进 `docs/architecture.md` 第 0–1 节）。

**出口标准**：第一条场景能用一句话说清，并且能手动验证（点一遍 / 发一条消息 / 跑一条命令）。

**常见错误**：替用户编需求；场景超过 5 条；把"以后可能用得上"写进这次范围。

---

## 阶段 1 · 技术线（**最常被跳过**）

**目标**：定下技术栈、硬约束与演进路线，让后面的架构有落脚点。

**动作**
1. 列出**硬约束**：必须用的语言/平台、预算上限、合规要求、团队熟悉度、已有代码。
2. 区分**单向门**（难换：数据库、部署平台、外部供应商、核心框架）与**双向门**（易换：格式化工具、小工具库）。单双向门要慎重并写 ADR；双向门快速决定，别纠结。
3. 对每个单向门给 **2–3 个候选**，按判断标准对比（成熟度、文档、可替换性、成本、许可证、社区活跃度）。
4. 找出**最不确定的一项**，做**限时原型（spike）**：限时一天，只验证可行性，验证完删掉，别让它变成正式代码。
5. 锁定版本，写进 README 与依赖锁定文件。

**产出物**：技术选型表（候选/标准/代价/决定/为什么）、技术风险清单、版本锁定、`docs/adr/0001-技术选型.md`。

**出口标准**：每个单向门都有理由；最不确定项已有原型结论；没有"因为教程用它"这类理由。

**常见错误**：跳过技术线直接写代码；因为火/因为 AI 推荐就选；选完不能换（深绑定）；用已停止维护的库。

**详见**：`tech-line.md`。

---

## 阶段 2 · 架构

**目标**：把系统切开、把依赖理顺、把数据和边界钉死。

**动作**
1. 按类型查 `project-types.md` 取子系统**候选**，再按实际裁剪（照抄清单 = 没做架构）。
2. **至少给两个候选拆法**，列代价，选一个并写明理由。只给一个方案 = 没给选择。
3. 用 `assets/blueprint-template.md` 逐项填空，不许留空。
4. 同时画：五层线、数据模型、部署形态、质量属性（**要数字**）。
5. 每个子系统给：名字、职责、**边界（不做什么）**、对外接口、依赖谁、被谁依赖。
6. 画依赖方向图，确认无环。
7. 借 C4 尺度对齐：产品=System，可独立部署单元=Container，内部功能块=Component（别把我们的"子系统"叫成"容器"）。

**产出物**：`docs/architecture.md`（图纸）+ 依赖图 + `docs/adr/`。

**出口标准**：评分表 ≥8 分（见 `acceptance.md`）；依赖无环；**每个子系统都能单独替换 + 单独测试**；没有两个子系统共写同一张表。

**常见错误**：只画代码层不画数据；质量属性写形容词；子系统超过 7 个或少于 2 个还硬拆；空目录凑层数。

---

## 阶段 3 · 契约（接口先行）

**目标**：在写实现之前，把"谁给谁提供什么"钉死。

**动作**
1. 逐模块列能力清单（一句话一条）。
2. 每条写清：输入、输出、出错情况（用该语言最常规的写法）。
3. 明确写出哪些是**内部细节，外部不许碰**。
4. 写**假实现**（返回固定值），先跑通调用方。
5. 定错误约定：错误码/异常类型/用户可见提示 vs 开发者可见信息。

**产出物**：接口清单、数据契约、错误约定、假实现。

**出口标准**：假实现能跑通调用方；换实现不改调用方。

**常见错误**：接口里掺实现细节；先写实现再补接口；接口跟着实现改。

---

## 阶段 4 · 工程化（工程基线）

**目标**：让项目**不会烂**。

**动作**：按 `engineering-baseline.md` 分级落地。任何项目必备四项：版本控制、密钥与配置分离、README、可回滚的部署方式；小项目再加依赖锁定、日志与错误、最小测试、格式化/lint、迁移脚本、最小 CI。

**产出物**：可运行的骨架 + CI 绿灯 + README + 迁移脚本目录 + `docs/adr/`。

**出口标准**：CI 绿灯；密钥不在代码里；**能回滚到上一版**。

**常见错误**：密钥进仓库；手改生产库；没有回滚方案；测试只测 mock。

---

## 阶段 5 · 实现

**目标**：按层推进，每批都可验收。

**动作**
1. 自下而上：接口 → 组件 → 模块 → 子系统。
2. **一次一个文件/一个模块**，小 diff（超过 300 行就该怀疑是不是又在"一次生成整个项目"）。
3. 每批按 `ai-code-acceptance.md` 八条过一遍，要求贴**真实执行输出**。
4. 每批结束同步更新图纸与 ADR。
5. 看不懂的代码不进主干：要么让它讲清楚（费曼检验），要么重写。

**产出物**：每批一个小 diff + 验收记录。

**出口标准**：每批自己跑过一遍；"完成"的声明都有命令与输出。

**常见错误**：接受"应该没问题"的结论；上下文太长还继续在同一会话里改（接口会被忘掉）。

---

## 阶段 6 · 交付上线

**目标**：能发布、能救火。

**动作**
1. 写清发布步骤与回滚步骤（都要真的执行过一次）。
2. 环境分离（本地/测试/生产配置不互串）。
3. 无人值守就要有**失败告警**，不能只写日志。
4. 有真实用户数据就要**备份 + 恢复演练**（只备份不演练 = 没有备份）。
5. 过一遍 `data-and-quality.md` 的"上线才发现清单"。

**产出物**：发布步骤、回滚步骤、告警、备份恢复演练记录。

**出口标准**：完成定义（DoD）全过（见 `acceptance.md`）。

**常见错误**：上线才想鉴权；测试脚本连了生产库；出事只能干看着。

---

## 阶段 7 · 演进

**目标**：需要时才升级复杂度，平时抵制提前设计。

**动作**
1. 建**技术债台账**：欠了什么、影响什么、什么时候还。
2. 升级只看信号表（`acceptance.md` 第五节），不看时间表、不看别人家。
3. 每次升级补一条 ADR，写清触发信号与代价。

**产出物**：技术债台账、升级记录 + ADR。

**出口标准**：每个升级动作都能对应一个已出现的信号。

**常见错误**：因为"以后用户会很多"提前上微服务/分库分表；重构没有回滚能力。

## 附：规模适配（缩范围，不降标准）

专业做法叫**按规模裁剪深度**（right-sizing）：裁的是**产出物范围**，不是质量底线。
判断依据不是"项目小所以少做"，而是"**这个阶段在这规模下需要多深**"。

| 规模 | 走到哪个阶段 | 产出物深度 | 绝不省 |
|---|---|---|---|
| 玩具 / 脚本（1 人几天） | 0 → 2（五层各一句话）→ 4（前三项） | 一页纸，不必分目录 | 密钥分离、README、能重跑 |
| 小项目（1 人几周） | 0–5 全走一遍 | 图纸一页 + 接口文件 + CI | 铁律 6 的全部五项 |
| 中型（多人/多端） | 0–7 全走 | 分文件图纸、ADR、环境分离 | 加上：接口契约自动化校验、告警 |
| 大型（多产品/多团队） | 0–7 + 治理 | 独立仓库/包、架构校验进 CI | 加上：依赖方向自动化断言、审计 |

**四档都要能回答的三个问题**：接口在哪、密钥在哪、出事怎么回滚。
**反面写法**："项目小所以不写测试/不做密钥分离"——这不是裁剪，是把风险推给未来的自己。
（对照实例：`assets/examples/03-cli-tool.md` 把"缩范围不降标准"算到了每一项。）
