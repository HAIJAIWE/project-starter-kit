# 分层线：系统 → 子系统 → 模块 → 组件 → 接口

适用于任何项目类型。层数概念永远在，**实现上可以省略目录**。

## 一、五层的完整定义

| 层 | 一句话职责 | 判定标准 | 边界（它不做什么） | 数量级 |
|---|---|---|---|---|
| **系统** | 能独立运行、对外交付价值的完整产品 | 有入口、能启动、能对用户给出一个结果 | 不写具体业务细节 | 1 个 |
| **子系统** | 系统里能独立替换/测试/发布的一大块 | 去掉它，系统少"一种能力"而非少"一个按钮" | 不碰别的子系统的内部 | 2–7 个 |
| **模块** | 子系统内部按功能分的抽屉，一个模块管一件事 | 能用一句话说清它管什么 | 不跨模块摸内部文件 | 每子系统 3–8 个 |
| **组件** | 模块里可复用、可替换的零件 | 别人能用、也能换；换掉它调用方不用改 | 不做流程编排决策 | 每模块若干 |
| **接口** | 规定怎么调用：输入、输出、出错 | 只有"是什么"，没有"怎么做" | 不掺实现逻辑 | 每个模块一份 |

数量级只用来提醒"别切太碎/太粗"。**切分标准永远是职责，不是行数。**

> **这不是行业标准，而是本套文档的内部约定。** 行业里没有统一的层级命名：C4 用 System / Container / Component，Clean Architecture 用同心圆，DDD 用限界上下文，各家公司的"模块 / 包 / 服务"含义也各不相同。
> 五层的作用只有一个：让任何一段代码都能回答三件事——**它在谁的边界里、它依赖谁、换掉它要改多少地方**。层级数量应该跟着项目规模变（见 `roadmap.md` 的规模适配表），五层是默认起点，不是必须。

对照几个主流体系（**同一样东西，不同叫法**）：

| 我们这套 | C4 model | Clean Architecture | DDD | 公司里的常见叫法 |
|---|---|---|---|---|
| 系统 | System | — | — | 产品 / 应用 |
| 子系统 | Container（可独立部署 / 测试的单元） | 层（同心圆的某一环） | 限界上下文 | 服务 / 模块 / 包 |
| 模块 | Component | Use Case / Adapter | 聚合 / 领域服务 | 目录 / 包 / 领域 |
| 组件 | Code element | Class | 实体 / 值对象 | 类 / 函数 / 文件 |
| 接口 | Port / Interface | Port | Repository 接口 | 契约 / API / 抽象 |

**成熟团队靠什么保证不乱**：① 边界按业务与团队划（Conway 定律）；② 方向用工具在 CI 里卡死（ArchUnit / dependency-cruiser / import-linter）；③ 决策写 ADR；④ 图用 C4。
**业余项目通常不显式做架构**——按功能分文件夹、靠约定和"能跑"撑着，等到改不动了才回头拆。这就是"越大越乱"的来源。

## 二、依赖铁律

**只能上层依赖下层，禁止循环。** 这是 Clean Architecture 的依赖规则（Dependency Rule），配合稳定依赖原则（SDP：依赖应指向更稳定的方向）。

```
系统
 └─ 子系统          ← 可依赖下层子系统（但要经过接口）
     └─ 模块        ← 可依赖同子系统内的下层模块
         └─ 组件    ← 可依赖接口
             └─ 接口 ← 谁都不依赖，最稳定
```

三条最常被违反的推论：

1. **下层不知道上层存在**：工具不该知道谁在调它；存储不该知道界面长什么样。
2. **越靠下越稳定**：接口的变化频率必须低于实现。
3. **同层可以互相依赖，但要经过接口**，否则等于把两层焊死。

**唯一例外：入口/装配模块**可以依赖所有模块，但谁都不许反过来依赖它。
跨层跳级（比如界面直接摸数据库）必须写进图纸并写明理由——"图省事"不算理由。

## 三、常见分层错误与修法

| 症状 | 说明 | 修法 |
|---|---|---|
| 循环依赖 A ⇄ B | 两个模块互相引用 | 共同需要的接口下沉到下层；或用事件反转方向 |
| 万能 utils / common | 什么都往里塞 | 按职责拆散，各回所属模块；`utils` 只放无业务含义的纯函数 |
| 一个文件干三层的事 | 入口 + 业务 + SQL 混在一起 | 按五层拆文件，先抽接口 |
| 接口跟着实现改 | 没抽象出稳定契约 | 从调用方视角重写，只留真正需要的输入/输出 |
| 模块说不清职责 | 出现"杂项""其他" | 拆到能一句话说清；说不清说明没找对边界 |
| 分层了但改一处崩三处 | 层间靠内部细节耦合 | 检查是否绕过接口直接访问内部文件 |
| 空目录凑层数 | 为"看起来分层"建单文件目录 | 小项目允许省略目录，别做样子工程 |

## 四、同名不同义（**最容易把小白绕晕的地方**）

"组件""容器""模块"在不同语境里含义不同，图纸里必须说清用的是哪一个：

| 词 | 我们图纸里的意思 | 别处常见的意思 | 怎么避免混淆 |
|---|---|---|---|
| **组件** | 模块里可替换的零件（一个文件/类/函数） | 前端的 UI 组件（React/Vue 组件、按钮、表单） | 图纸里写"架构组件"；UI 组件归到界面子系统的界面模块下，是**模块内的一种组件**，别和架构层混谈 |
| **容器** | 不用于分层（我们只说子系统） | C4 模型里的 container（可独立部署单元）、Docker 容器 | 谈部署时说"部署单元"；谈 Docker 就直说 Docker |
| **模块** | 子系统内部按功能分的抽屉（目录级） | 语言层面的 module/package（一个文件） | 说"模块"时补一句"目录级还是文件级" |
| **接口** | 调用契约（输入/输出/错误） | HTTP 接口 / REST API | 对外 HTTP 接口属于接入子系统，和内部契约分开写 |

借 **C4 模型**的尺度对齐一下（不必背，用来防止把话说拧）：我们的「系统」≈ C4 的 System，「子系统」≈ C4 的 Container（可独立部署/独立测试的单元），「模块/组件」≈ C4 的 Component。**别用 C4 的"容器"去称呼我们的子系统**，否则一谈 Docker 就全乱。

## 五、层 × 测试 × 部署（哪层必须自动化）

| 层 | 测试要求 | 部署归属 |
|---|---|---|
| 接口 | **必须有**自动化测试（用假实现验证契约） | 随所属模块走 |
| 组件 | 业务组件**必须有**；纯工具函数抽查 | 随所属模块走 |
| 模块 | 集成测试：模块内部能跑通 | 随所属子系统走 |
| 子系统 | 能单独启动/单独跑测试（**这是判定它是不是子系统的硬指标**） | 可独立部署 → 独立部署单元 |
| 系统 | 端到端：至少第一条关键场景能自动跑 | 部署拓扑见 `project-types.md` |

原则：**越靠下越要多测**（改一次跑一次很便宜）；界面层手测为主，别为了覆盖率给 UI 写一堆脆测试。

## 六、数据模型放在哪

- **表/集合结构**、字段含义、谁写谁读 → 属于**数据子系统**，但它服务的是业务子系统，所以契约要在接口层写清。
- **迁移脚本**（建表、改字段）单独一个目录，按顺序编号，**永远不手改生产库**。见 `engineering-baseline.md`。
- 判定边界的一招：**一张表如果被两个子系统写，说明子系统切错了**——要么合并，要么把写权限收到一个子系统，另一个只读接口。

## 七、目录映射（语言无关）

关键是**目录层级必须能读出层次**：

```
项目/
├── <子系统A>/
│   ├── <模块1>/
│   │   ├── 接口定义            ← 契约，谁都不依赖它
│   │   └── 组件...            ← 一个文件一个组件
│   └── <模块2>/
├── <子系统B>/
├── <共享子系统>/              ← 被多个子系统复用的接口与基础组件
└── 入口/装配                  ← 唯一知道所有人的地方
```

各语言的习惯落点（**只是举例，不是要求**）：

| 概念 | TypeScript | Python | Java / C# | Go |
|---|---|---|---|---|
| 子系统 | `packages/*` | 独立包/目录 | Maven/Gradle module | module |
| 模块 | `src/<模块>/` | `<pkg>/<模块>/` | `package` | `internal/<模块>/` |
| 接口 | `types.ts` 的 `interface` | `Protocol` / `ABC` | `interface` / 抽象类 | `interface` |
| 组件 | 一个 `.ts` 文件一个类/函数 | 一个模块文件 | 一个 class | 一个 struct + 方法 |

**"每个模块都有 types.ts"不是教条**。教条是"每个模块都有稳定的对外契约"，文件叫什么随语言习惯。

## 八、重构顺序（自下而上，五步）

1. **找接口** — 先把每个模块"对外承诺什么"写成契约，不写实现。
2. **组件归位** — 每个零件回到所属模块，一个文件一件事。
3. **模块贴标签** — 目录名 = 职责名。
4. **子系统拆开** — 能独立测试/替换的大块独立出去。
5. **定依赖方向** — 画依赖图，消除环，确认单向。

**从零起项目时顺序反过来**：先出图纸，再自下而上把接口和组件填进去。

## 九、循环依赖怎么查

人肉版（任何语言都适用，先做这个）：列出"谁引了谁"→ 画箭头 → 能走回起点就是环 → 环上**最稳定的概念**下沉为接口。

工具版（有就用，没有别为它停工）：

| 语言/生态 | 工具 |
|---|---|
| JS / TS | `madge --circular`、`dependency-cruiser` |
| Python | `pydeps`、`import-linter`（分层契约可写进配置） |
| Java / Kotlin | `ArchUnit`、`jdeps` |
| Go | `go list -deps`、`go-arch-lint` |
| C# | `NetArchTest` |
| Rust | `cargo modules`、`cargo-deny` |

`import-linter` 与 `ArchUnit` 的价值：把分层规则写成可执行断言，CI 里一跑就知道有没有人越界。

## 十、起系统：一个产品往往不止一个系统

最常见的误解是"一个产品 = 一个系统"。除了玩具脚本，产品通常由多个**系统**组成，它们各自能独立运行，之间**只通过接口或事件说话**：

| 系统 | 管什么 | 典型技术形态 |
|---|---|---|
| 客户端系统 | 界面、交互、本地状态 | 网页 / App / 小程序 / 桌面程序 / 聊天机器人外壳 |
| 服务端系统 | 业务规则、对外接口、权限 | 后端服务 / 云函数 |
| 数据系统 | 存储、迁移、备份、报表 | 数据库 + 迁移脚本 + 备份任务 |
| 运维系统 | 日志、告警、部署、调度 | CI/CD + 监控 + 定时任务 |

**怎么判断该分成几个系统**（不是越分越好）：

1. 能不能**单独替换**？（换掉网页端不影响服务端 → 该分）
2. 能不能**单独重启/发布**？（重启爬虫不该中断网站 → 该分）
3. 有没有**不同的运行环境**？（一个跑用户手机、一个跑服务器 → 该分）
4. 有没有**不同的信任级别**？（密钥只能在服务端 → 客户端绝不能碰）

三条都答"不能/没有"，就还是一个系统，别拆。
**硬规矩**：客户端系统里永远不放密钥与业务裁决权；系统之间共享数据库 = 立刻退化成"分布式单体"，比单体更糟。
