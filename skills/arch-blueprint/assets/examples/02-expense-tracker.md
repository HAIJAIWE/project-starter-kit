# 样板图纸 2：个人记账网站（小项目 · 有真实用户数据 · 要能备份）

> 填满的实例。重点看：**为什么否掉了"前后端分离"**、**金额怎么存**、**备份怎么算数**、以及**i18n 什么时候才需要**。
> 规模：小项目。类型：Web 应用（含登录与数据持久化）。

---

## 阶段 0 · 立项与边界

- **给谁用**：我和家人（2–5 人），私人使用，不对外开放注册。
- **完成什么动作**：手机上 30 秒内记一笔支出；月底看汇总。
- **从哪用**：手机浏览器（网页即可，不做 App）。
- **数据**：收支记录（金额、分类、日期、备注）。**私有、不能丢**。
- **外部**：无第三方（不接银行、不接支付）。
- **跑在哪 / 谁维护**：一台小服务器；我一个人维护。
- **成本上限**：每月不超过一顿饭钱。

### 关键场景
| # | 场景 | 这次做吗 |
|---|---|---|
| 1 | 手机上登录 → 记一笔 → 看到今天已记 3 笔 | **做（MVP）** |
| 2 | 看本月分类汇总 | 做（第二条） |
| 3 | 导出 CSV 给家人看 | 做 |
| 4 | 多人协作账本 / 共享预算 | 以后再说 |
| 5 | 多币种、出国记账 | 以后再说 |

### 不做清单
不做公开注册、不做多币种、不做多语言、不做移动 App、不做银行账单导入、不做预算提醒。

---

## 阶段 1 · 技术线

### 硬约束
| 约束 | 内容 | 影响 |
|---|---|---|
| 人力 | 一人维护，非全职 | 减少活动部件，优先"少而稳" |
| 数据 | 不能丢，含家人账单 | 备份 + **恢复演练**是硬要求 |
| 设备 | 主要在手机上用 | 必须响应式，首屏轻 |
| 隐私 | 家庭财务数据 | 不接第三方分析、不把数据发给外部 |
| 预算 | 每月一顿饭钱 | 一台小服务器 + 对象存储足够 |

### 单向门 vs 双向门
| 决策 | 类型 | 决定 |
|---|---|---|
| 数据库 | **单向门** | 关系型数据库（金额与汇总查询天然适合；换库成本高） |
| 部署平台 | **单向门** | 一台常驻小服务器（避免被某个平台的定价/限制锁死） |
| 认证方式 | **单向门** | 先用成熟框架自带的会话机制；不自己写加密 |
| 前端方案 | 双向门（但影响活动部件数量） | 见阶段 2 的方案对比 |
| 图表库、CSS 工具 | 双向门 | 快决定 |

### 限时原型（各半天）
1. **托管环境能连数据库吗？备份能导出吗？** → 能，但导出要写脚本（**进交付清单**）。
2. 手机上录入表单好不好用？→ 数字键盘 + 大按钮，需要专门处理（进界面设计）。

## 阶段 2 · 架构

### 候选拆法对比
| 方案 | 怎么拆 | 优点 | 代价 | 选它吗 |
|---|---|---|---|---|
| A | 前后端分离：前端框架 + 独立 API 服务 | 交互体验好；将来能接 App | **两个部署单元、两套构建、两处调试、跨域与鉴权成本**；一人维护时活动部件翻倍 | 否 |
| B | 服务端渲染单体：一个服务，模板渲染页面 | 一个部署单元、一套构建、直接会话鉴权、首屏轻 | 交互复杂时不如前端框架灵活 | **是** |

选 B 的理由：**一个人维护的小项目，活动部件数量是第一成本**。"将来可能接 App"不是现在的需求（进"以后再说"）。
> 这正是 `patterns.md` 里"默认路径"的落地：模块化单体优先，团队/规模信号出现再拆。

### 子系统与依赖

| 子系统 | 职责 | 边界 | 能单独测？ |
|---|---|---|---|
| 界面与路由 | 页面渲染、表单、会话 | 不做业务计算 | 是（关键场景走查） |
| 记账业务 | 校验、分类、汇总计算 | 不直接写 SQL | 是（**核心单测在这**） |
| 存储与迁移 | 读写、迁移脚本、备份 | 不懂业务语义 | 是 |
| 认证 | 登录、会话、权限 | 不做业务规则 | 是 |

依赖方向：界面 → 业务 → 存储；认证被界面与业务依赖；**业务不知道界面存在**。

### 数据模型
| 实体 | 关键字段 | 谁写（唯一） | 生命周期 |
|---|---|---|---|
| 用户 | id、昵称、密码哈希、创建时间 | 认证 | 注销即删 |
| 账目 | id、user_id、金额（**整数，单位分**）、类型（收/支）、分类、日期(UTC)、备注、创建时间、删除标记 | 记账业务 | 用户删除后 7 天内可恢复，之后真删 |
| 分类 | id、user_id、名称、排序 | 记账业务 | 随用户 |

- 金额：**整数存分**（浮点存钱是经典事故）。
- 日期：存 UTC，展示按本地时区；"今天"的边界按用户时区算。
- 删除：软删（删除标记）+ 定时真删；**每个查询都带删除过滤**，否则"删了还能查到"。
- 备份：每天导出数据库快照到对象存储，保留 30 天；**每季度真的恢复一次**。

### 质量属性（数字）
| 属性 | 要求 | 架构后果 |
|---|---|---|
| 性能 | 手机首屏 2 秒内；记一笔 1 秒内 | 服务端渲染 + 少量静态资源；单页不做重型前端 |
| 可用性 | 挂了可以几小时不可用（家人不会半夜记账） | 单机 + 进程守护足够，不做集群 |
| 数据安全 | **不能丢**；只有家人能看 | 每日备份 + 恢复演练；登录 + 会话；数据库不外露端口 |
| 隐私 | 不接第三方统计/广告 | 不引分析 SDK；日志不含金额与备注 |
| 成本 | 每月一顿饭钱以内 | 单台小服务器 + 少量对象存储 |
| 可维护 | 三个月后我还看得懂 | 模块化单体、无前端构建链、注释写"为什么" |

### 部署形态
小服务器（进程守护 + 反向代理 + HTTPS）→ 每日备份脚本 → 发布 = 拉代码 + 跑迁移 + 重启；回滚 = 切上一版本目录 + 重启（迁移脚本要能前向修复，见 `release-and-evolution.md`）。

## 阶段 3 · 契约

| 接口 | 输入 | 输出 | 出错 |
|---|---|---|---|
| `createEntry` | 用户、金额(分)、类型、分类、日期、备注 | id | 金额 ≤0 / 分类不属于该用户 → 明确错误 |
| `listEntries` | 用户、时间范围、分页 | 列表 + 总数 | — |
| `monthlySummary` | 用户、年月 | 收入/支出/按分类合计 | — |
| `deleteEntry` | 用户、id | 成功 | **不是本人的 → 403（越权校验）** |
| 页面路由 | 表单参数 | 重定向 + 提示 | 校验失败 → 回到表单并保留输入 |

- 错误分两类：**用户错误**（给页面提示）与**系统错误**（记日志 + 通用提示，不暴露堆栈）。
- 假实现先跑通：`monthlySummary` 返回固定数字，先把页面流程走通。

## 阶段 4 · 工程化

必备四项全做：版本控制 / 密钥分离（会话密钥、数据库密码在 `.env`）/ README（含备份与恢复步骤）/ 可回滚部署。
另加：迁移脚本（幂等）、最小 CI（跑单测）、日志（不含金额备注）、**备份 + 恢复演练**、限流（登录失败次数）。
测试最小集：金额与汇总计算单测、`createEntry` 校验、一条"改坏实现就变红"的汇总测试。

---

## 阶段 5 · 实现顺序

1. 登录与会话 → 2. 记一笔（假汇总）→ 3. 列表与分页 → 4. 月汇总（真计算）→ 5. 删除与软删过滤 → 6. 导出 CSV → 7. 备份脚本 + 恢复演练。

---

## 阶段 6 · 交付

- 发布步骤写成脚本；迁移先跑、后切流量。
- 回滚步骤演练一次（切目录 + 重启 + 数据是否需要前向修复）。
- 告警：服务不可用/备份失败要能通知自己。
- 上线前过 `data-and-quality.md` 的"上线才发现清单"（时区、金额、并发、重复提交尤其相关）。

---

## 阶段 7 · 演进

| 升级 | 触发信号 |
|---|---|
| 公开注册 | **基本不会做**——一旦开放，安全与合规成本陡增（这是清醒的放弃，不是遗漏） |
| 前后端分离 / App | 手机网页真不够用，且有人愿意持续维护第二套 |
| 多币种 | 真的有外币账目 |
| i18n（多语言） | 有非中文使用者要记账（见 `i18n-and-a11y.md`） |
| 图表 / 预算 | 汇总页面看得不够，明确要趋势 |
| 银行账单导入 | 手动录入成为主要痛点（且要处理格式与合规） |

---

## 现在不做什么

| 排除 | 为什么 | 什么信号出现才做 |
|---|---|---|
| 前后端分离 / 移动 App | 一人维护，活动部件数量是第一成本 | 网页体验真的不够用 |
| 公开注册 | 安全与合规成本远超收益 | 不打算做（清醒放弃） |
| 多币种 / 多语言 | 无此需求 | 出现外币或外语使用者 |
| 银行账单导入 | 解析复杂 + 合规风险 | 手动录入成为主要痛点 |
| 第三方统计/广告 | 隐私优先 | 不做 |
| 集群/高可用 | 家人不会半夜记账 | 有公开用户且影响收入 |

## 待确认
- 服务器所在区域的时区与夏令时规则（影响"今天"的边界）。
- 备份保留期是否符合家人对隐私的预期。
