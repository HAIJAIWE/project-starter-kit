# Arch Blueprint（起项目全流程）

**定位**：一条主线——从想法到"能跑、能交、能改"。**一次只推进一个阶段**，可回退，不许跳。
**适用**：任何项目类型（网站、后端 API、移动/小程序、桌面、CLI、机器人、AI/智能体、爬虫报表、插件、游戏、内部工具、库/SDK、IoT、电商）。
**不适用**：非软件的事、纯业务咨询、"帮我把整个项目写完"（本技能教**怎么起**，不替人写完）。

核心信念：**先图纸再动手；技术线不明确就不写实现；不为模式而模式；不引用说不清出处的方案；底线不降。**

## 两种用法

| 用法 | 怎么走 | 主产出 | 谁主导 |
|---|---|---|---|
| **起项目**（0 → 能跑） | 下面第一节的八阶段主线 | 图纸 + 契约 + 骨架 + ADR + 交付清单 | 本技能 + 「项目领航员」角色 |
| **看项目**（给已有项目体检） | **不走主线**：先 `references/acceptance.md`（评分表 + 代码质量门）→ 再 `../software-architect/references/review-checklist.md` → 多视角时 `references/team-brief.md` | 风险清单（位置 / 触发条件 / 影响 / 最小修法 / 验证）+ 放行条件 | 架构师角色；多视角时用技术评审团 |

**评审路径三条纪律**（面对别人的既有代码，比"起项目"更严）：① **只报告不修改**，每条给「位置 / 为什么算问题 / 最小修法 / 严重度」；② **每条可定位**（`文件:行` + 触发条件），**没跑过的检查只能列为计划**；③ **区分**已复现问题 / 设计风险 / 材料缺口。
体检**不产出图纸**；体检后决定重构，才切回八阶段主线。**只装了本技能时**：用 `acceptance.md` 评分表 + 各 reference 自带的检查清单代替 review-checklist。

## 输出纪律（硬性，优先级高于本文其它章节）

**这套文档是给 AI 执行的，不是给人读的教程**；用户可能完全不懂技术。因此：

1. **少说多做**：默认直接产出文件、代码、配置、清单；**不要写方法论演讲，不要复述本文档里已有的清单**。
2. **结论先行**：先给结论与产出物，再给必要的 1–3 句理由。**不写"总结""展望""进一步优化建议""希望对你有帮助"这类填充段落。**
3. **交付即可运行**：给**完整文件**而不是片段；每批交付附**一条能跑的命令**（或一个能点的动作）和预期结果。
4. **依赖克制**：默认**零新增依赖**（只用标准库与项目已有依赖）。确实需要时，先说清"为什么标准库不行"，并确认它真实存在、装得上；装不上就换实现，**不许硬编 API**。
5. **不装懂**：不确定就写"不确定 / 需要验证"，不用"通常""一般来说""建议考虑"兜。**没跑过的检查只能列为计划。**
6. **不解释用户没问的东西**；一次最多问 4 个澄清问题，其余先按假设做，并把假设写出来。
7. **结尾是产出物**（文件路径 / 命令 / 结果），不是感悟。

## 一、八阶段主线（明细见 `references/roadmap.md`）

| 阶段 | 关注点 | 必须落成文件 | 出口标准 |
|---|---|---|---|
| **0 立项与边界** | 给谁用、这次做到哪 | 一句话说明、3–5 关键场景、不做清单 | 第一条场景能一句话说清 |
| **1 技术线** | 硬约束、单向门、最不确定项 | 选型表、风险清单、ADR | 单向门有理由；不确定项已用限时原型验证 |
| **2 架构** | 切开、理顺依赖、钉死数据与边界 | 图纸（五层 + 数据 + 质量属性 + 依赖图） | 评分表 ≥8 分、无环、每个子系统能单独测 |
| **3 契约** | 谁给谁提供什么 | 接口清单、错误约定、假实现 | 假实现跑通调用方 |
| **4 工程化** | 项目会不会烂 | 密钥分离、测试、CI、迁移、回滚、环境可复现 | CI 绿灯 + 能回滚 |
| **5 实现** | 一次一层怎么推 | 小 diff + 验收记录 | 每批过 AI 代码验收八条 |
| **6 交付上线** | 怎么发、出事怎么办 | 发布/回滚步骤、告警、备份演练 | 完成定义（DoD）全过 |
| **7 演进** | 何时升级、何时不做 | 技术债台账、升级信号 | 每个升级都有触发信号 |

每阶段结束同步更新 `docs/architecture.md` 与 `docs/adr/`。**阶段 4–6 的落地推进方式（里程碑、可交付切片、上线资源与合规、上线后运营）见 `references/shipping.md`。**

## 二、五层线（架构阶段核心）

| 层 | 职责 | 判定标准 |
|---|---|---|
| **系统** | 能独立运行、对外交付价值的完整产品 | 有入口、能启动、能给结果 |
| **子系统** | 能独立替换/测试/发布的一大块 | 去掉它少"一种能力"而非"一个按钮" |
| **模块** | 子系统内部按功能分的抽屉 | 能一句话说清它管什么 |
| **组件** | 模块里可复用、可替换的零件 | 换掉它调用方不用改 |
| **接口** | 规定怎么调用：输入、输出、出错 | 只有"是什么"，没有"怎么做" |

**五层只是"结构"这一个维度。** 完整架构要回答下面 **8 维**（缺一维就会在某个阶段返工，每一维都有对应文件）：

| # | 维度 | 要回答什么 | 产出物 | 少了会怎样 | 在哪 |
|---|---|---|---|---|---|
| 1 | **结构分层** | 系统 → 子系统 → 模块 → 组件 → 接口 | 子系统表 + 目录树 | 文件放错层，越写越乱 | `references/layering.md` |
| 2 | **依赖方向** | 谁依赖谁、有没有环、跨层跳级有没有理由 | 依赖图 | 循环依赖，改一处崩三处 | `references/layering.md` |
| 3 | **数据与归属** | 有哪些实体、**谁写**哪张表、活多久 | 数据模型表 | 两个子系统共写一张表 → 边界是假的 | `references/data-and-quality.md` |
| 4 | **接口契约** | 谁给谁提供什么、输入 / 输出 / 出错 | 接口清单 + 假实现 | 接口跟着实现改 → 返工 | `references/api-contract.md` |
| 5 | **部署形态** | 跑在哪、怎么发、怎么回滚 | 部署拓扑 | 单人小项目被拆成 6 个包 | `references/project-types.md` |
| 6 | **质量属性** | 多少人用、多快算能接受、多贵、多安全（**要数字**） | 数字表 | 上线才发现要加队列 / 鉴权，全盘重排 | `references/data-and-quality.md` |
| 7 | **横切关注点** | 配置与密钥、日志与可观测、错误、认证授权、多语言 | 工程基线清单 | 密钥进仓库、出事查不到原因 | `references/engineering-baseline.md`、`references/security-checklist.md`、`references/i18n-and-a11y.md` |
| 8 | **演进** | 何时升级、技术债何时还 | 信号表 + 债务台账 | 提前上微服务，或永远不动 | `references/release-and-evolution.md` |

> **图纸模板的 14 节就是按这 8 维展开的**（`assets/blueprint-template.md`）——填完模板 = 逐维回答完毕。
> 结构风格的选择（分层 / 垂直切片 / 六边形 / EDA / CQRS / 微内核 / 云函数 / 微服务）连同**触发条件与代价**见 `references/patterns.md`。

完整定义、边界判定、同名不同义、层×测试×部署、多系统 → `references/layering.md`。

## 三、铁律

1. **五层线固定**：谈任何代码先回答"它在哪一层"；答不上来 = 位置错了。
2. **依赖单向**：只上层依赖下层，禁止循环；跨层跳级要写理由。唯一例外是入口/装配模块。
3. **接口先行**：先定契约再写实现；**换实现不改调用方**才算接缝对了。
4. **一次只推进一层/一个阶段**：禁止一次回复吐出整个项目。
5. **不为了模式而模式**：默认「模块化单体 + 分层」（业务多了转垂直切片）；AI 项目再加「单智能体 + 工具」。微服务 / monorepo / 事件驱动 / CQRS / 消息队列 / 多智能体必须先满足触发条件。
6. **底线不降**：接口契约、密钥分离、能回滚、README、至少一条真测试——再小也不省。
7. **三条代码级底线**：外部输入在边界校验；跨进程调用必须有超时、只重试幂等操作、关键写操作要幂等键、不写空 catch；看不懂的代码不进主干、不留硬编码密钥与调试打印。

## 四、规模适配：缩范围，不降标准

按规模裁剪**产出物深度**，不裁质量底线；判断依据是"这个阶段在这规模下需要多深"，不是"项目小所以少做"。四档对照表（玩具 / 小项目 / 中型 / 大型）见 `references/roadmap.md` 末尾。**任何规模都要答得出**：接口在哪、密钥在哪、出事怎么回滚。

## 五、取舍与出处要求

- **至少给两个候选方案**并列代价；只给一个 = 没给选择。关键决策落 `docs/adr/`。
- **引用必须给出处**（优先标准 / 官方文档）；**说不清出处的就不写**——禁止编造仓库名、目录结构、模式名、版本号，禁止拿小众包当行业范例；提到参考项目要说清"这是某一家的做法"。
- 图纸类产出用**表格 + 目录树 + 依赖图**，不写散文；每个结论后跟"怎么验证"。

## 六、看到这些就纠正

技术线没定就写代码；一上来就微服务 / monorepo / 事件驱动 / CQRS / 多智能体；一个文件塞入口 + 业务 + 存储；先写实现再补接口；循环依赖；只按技术分层让业务散落；AI 生成一大段却没人能说出它在哪一层、也没人真跑过；把 `utils/`、`common/` 当垃圾桶或空目录凑层数；省掉密钥分离 / 回滚 / 测试。
