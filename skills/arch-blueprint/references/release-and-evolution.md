# 版本控制、发布与演进（怎么改而不出事）

代码写出来只是开始，**改动才是日常**。这一份解决"怎么安全地一直改"。

---

## 一、版本控制最小纪律

| 项 | 做法 |
|---|---|
| 主干可用 | 主分支随时能跑（改坏就在分支上改） |
| 小提交 | 一次提交做一件事；超过 300 行就该拆（和 AI 协作同一条规矩） |
| 提交信息 | 说清**为什么**改，不只是"改了什么"；修 bug 关联现象 |
| 提交前 | 跑测试；别提交调试打印与临时开关 |
| 分支 | 单人用短分支即可；多人用 PR + 至少一人看（自己看也过清单） |
| 回退 | 已推送的历史**用 revert，不改写历史**（force push 会害到别人） |
| 忽略文件 | `.gitignore` 排除密钥、依赖目录、构建产物、本地数据库、大文件 |
| 大文件 | 别进仓库（历史里的东西删不干净；需要就外置存储） |

**关键动作**：任何时候都要能回答"上一版是什么、怎么回去"。

## 二、依赖与版本管理

- **语义化版本（SemVer）**：`MAJOR.MINOR.PATCH` —— 主版本=破坏性变更、次版本=兼容新增、修订=兼容修复。**看到 MAJOR 变化要读迁移说明。**
- 保留锁文件；锁定是为了可复现，不是为了永不升级。
- **定期主动升级**（建议每个季度），比攒一年再升便宜得多。
- 升级前读 CHANGELOG；破坏性变更要有迁移方案与回滚路径。
- 依赖越少越好：每加一个都要问"标准库能不能做、谁维护、许可证允许吗"。

## 三、发布（可重复，不靠记忆）

- 版本号 + tag；发布步骤写成脚本或 CI 任务（**手敲命令的发布迟早出错**）。
- **CHANGELOG**：给人看的变更列表（新增/修复/破坏性变更）。
- 发布前过一遍：测试绿、迁移脚本就绪、回滚步骤确认、告警就绪。
- 出问题的第一选择是**回滚**，不是现场热修（热修留到稳定后再说）。

## 四、渐进发布（把风险切小）

| 手段 | 用途 |
|---|---|
| **功能开关（feature flag）** | 新功能藏在开关后，出问题**秒关**，不用重新部署 |
| 灰度 / 小流量 | 先给自己/一小部分用户用，再逐步放量 |
| 蓝绿 / 流量切换 | 新旧两套环境，切流量即回滚 |
| 影子运行 | 新逻辑只算不生效，对比结果是否一致 |

**开关不是免费的**：上线稳定后要清理，否则开关会越积越多（属于技术债）。

## 五、数据迁移与兼容（最容易出事的一类）

- **扩展–收缩（expand–contract）**：先加新字段（兼容）→ 双写/回填 → 切换读取 → 确认无旧用法 → 再删旧字段。
- **绝不**在一步里同时改结构又删旧字段（回滚时数据就没了）。
- 迁移脚本要能重跑（幂等）；上线前在真实数据副本上演练一次。
- 备份在迁移前做，且**确认能恢复**（见 `engineering-baseline.md`）。

## 六、重构与替换（怎么改而不崩）

1. **小步 + 每步保持绿灯**：一次一个动作（改名 → 抽函数 → 移文件），每步跑测试。
2. **行为不变的重构与功能变更分开提交**，否则 review 和回滚都没法做。
3. **Strangler Fig（Martin Fowler）**：新实现与旧实现并存 → 逐步把流量切过去 → 旧实现无人用后删除。比"停机大改"安全得多。
4. 重构前先补测试：没有测试的重构就是赌博（`testing-strategy.md`）。

## 七、什么时候才该"重写"

重写几乎总是最后选项。满足下面多条才考虑：

- [ ] 改一个 bug 要动很多处，且每次都会引入新 bug
- [ ] 核心逻辑没人能读懂（包括作者自己）
- [ ] 依赖的平台/语言已停止支持
- [ ] **已有测试或能并跑新旧两套**（没护网的重写=把 bug 重写一遍）
- [ ] 业务能接受一段时间不加快功能

否则就按上面第六条渐进替换。

## 八、技术债台账（有意识欠债，比无意识烂掉好）

| 欠了什么 | 影响 | 什么时候还 | 触发条件 |
|---|---|---|---|
| 例：登录没有限流 | 可能被爆破、被刷短信费 | 有真实用户前 | 对外开放注册时 |
| 例：日志没结构化 | 排查慢 | 接入告警前 | 无人值守运行时 |

每条债都写清"什么时候必须还"，避免变成永久。

## 九、交付前发布自查

- [ ] 主分支能跑？发布步骤可重复？
- [ ] 回滚步骤写过，且**演练过**？
- [ ] CHANGELOG 更新了？
- [ ] 破坏性变更通知了调用方（含自己写的老客户端）？
- [ ] 迁移脚本幂等、演练过、有备份？
- [ ] 功能开关默认关闭，开关负责人明确？
- [ ] 依赖升级过、锁文件在、无已知高危漏洞？
