# 技术线：技术栈 + 硬约束 + 演进路线

技术线是很多项目最先烂掉的地方，也是最容易跳过的一步：**直接开始写代码 = 把选型决定交给了第一个教程**。
技术线不是"选个语言"，而是回答三件事：**受什么约束、用什么做、以后怎么换**。

---

## 一、三问法（半小时能问完）

### 问 1：硬约束有哪些？（先写约束，再选技术）

| 约束类型 | 要问的 | 影响 |
|---|---|---|
| 语言/平台 | 必须用某个语言吗？跑在别人平台上吗？ | 直接砍掉大半候选 |
| 预算 | 每月最多花多少（服务器 + 数据库 + 模型 + 短信/带宽）？ | 决定自建还是用托管服务 |
| 合规/隐私 | 数据敏感吗？能不能出境/发给第三方（含大模型）？ | 决定能不能用某些云与模型 |
| 团队 | 谁维护？他熟什么？一个人还是多人？ | **不熟的技术 = 运维成本翻倍** |
| 现状 | 已有代码/数据库/接口吗？ | 兼容优先于"更优" |
| 时间 | 多久要有第一个能给人看的东西？ | 决定用托管方案还是自建 |

**约束是硬门槛：不满足的候选直接删，不要"评估一下"。**

### 问 2：哪些是单向门？（决策可逆性）

借鉴 Amazon 的 **one-way door / two-way door** 决策理念：

| 类型 | 例子 | 该怎么做 |
|---|---|---|
| **单向门**（换了会痛） | 数据库类型、部署平台、外部供应商/大模型、核心框架、数据模型、对外接口格式 | 给 2–3 个候选、列代价、写 ADR、留验证时间 |
| **双向门**（容易换） | 格式化工具、日志库、小工具函数、目录名 | 快速决定，别开会讨论 |

**判断口诀**：换掉它要改多少文件、要迁多少数据、多久不能上线？答案越大，越是单向门。
对单向门，唯一可靠的保险是**在它前面加一层接口**（端口适配器），别让业务代码直接认它。

### 问 3：最不确定的是哪一项？

列 1–3 件"如果它不行，整个方案要重来"的事（比如：平台允许自动发消息吗？模型响应速度够吗？那个第三方接口能拿到我要的数据吗？）。
对每件做**限时原型（spike）**：

- 限时 **一天以内**，目标只有一个：**能不能做到**。
- 用最脏最快的写法，不写测试、不做结构。
- 结论写进 ADR：能做到 / 做不到 / 有条件能做到（条件是什么）。
- **验证完就删掉**，别让它变成正式代码（这是抛弃型原型）。

## 二、选型评估维度（对比候选时逐条打勾）

| 维度 | 怎么判断 | 红灯信号 |
|---|---|---|
| 成熟度 | 有真实的生产案例吗？出问题能搜到答案吗？ | 只有 demo，没有生产案例 |
| 维护活跃 | 最近有提交/发版吗？有安全公告响应吗？ | 一年没更新、作者失联 |
| 文档质量 | 官方文档能照着跑通吗？有升级指南吗？ | 只有 README 和一堆博客 |
| 可替换性 | 换掉它要改多少地方？有标准协议吗？ | 业务代码里到处是它的类型 |
| 成本模型 | 按量还是包月？涨价了怎么办？超限怎么表现？ | 免费额度用完直接停服 |
| 许可证 | 商用允许吗？有传染性条款吗？ | 商用受限、协议不明 |
| 与团队匹配 | 维护的人熟它吗？ | 只有"看起来很酷" |
| 版本策略 | 有 LTS 吗？破坏性变更多久一次？ | 频繁大版本重写 |
| 部署形态匹配 | 和项目要跑的地方合得来吗？ | 为了用它得额外搭一套基础设施 |

**打分不是为了算出总分，是为了暴露"你其实没得选"。**

## 三、默认起点（没有特殊理由就用，用户有偏好就听用户的）

| 场景 | 默认起点 |
|---|---|
| 通用数据存储 | 关系型数据库；本地小工具用嵌入式数据库 |
| 后端 | 该语言的原生主流 Web 框架，单个可部署单元 |
| 前端 | 一个自带路由与构建的成熟框架，别手写打包配置 |
| 对外接口风格 | 先 REST；前端字段需求多变再考虑 GraphQL |
| 部署 | 先一台机器/一个托管平台，能手动回滚；流量真的上来了再谈扩容 |
| 模型调用（AI 项目） | 官方 SDK，**包在自己的接口后面**，方便换供应商与降级 |
| 消息/异步 | 先同步调用；真的要削峰再上队列 |
| 定时任务 | 系统自带的定时器；别为此单独起一个服务 |

**规则**：选"出问题能搜到答案"的，不选"看起来很酷"的；**版本号必须真实存在**，写进文档前先去官方源确认。

## 五、反模式（看到就纠正）

| 反模式 | 为什么错 |
|---|---|
| 因为教程/网红/AI 推荐就选 | 别人的约束不是你的约束 |
| 跳过硬约束直接选最火的 | 会因为预算、合规、平台限制推倒重来 |
| 对双向门反复纠结 | 浪费的是最贵的时间 |
| 对单向门草率决定 | 数据库和供应商换起来是全量返工 |
| 业务代码直接认某个供应商的类型 | 换不了，等于被绑定 |
| 用没人维护的库 | 出安全问题时没人修 |
| 没有版本锁定 | 今天能跑明天不能跑 |
| 把"以后可能用得上"算进选型 | 提前引入复杂度，且大概率用不上 |
| 选完不写 ADR | 三个月后没人知道为什么，会反复推翻 |

## 六、怎么保证以后能换（演进策略）

1. **接口隔离**：所有外部依赖（数据库、云服务、模型、支付）都放在自己的接口后面，业务只认接口。
2. **依赖最少化**：每新增一个第三方库都要回答"标准库能不能做"。
3. **版本锁定 + 定期升级**：锁定版本，但每个季度主动升一次（避免攒成一次大爆炸）。
4. **数据可导出**：上线前就想好"如果换供应商，数据怎么拿出来"（很多平台故意难导出）。
5. **ADR 留痕**：每个单向门一条记录：背景 / 候选 / 决定 / 后果 / 什么时候该重新评估。
