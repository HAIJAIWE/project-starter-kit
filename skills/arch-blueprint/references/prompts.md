# 可直接复制的提示词模板

给不熟工程的人用：**照抄，把方括号替换成自己的内容。** 一次只发一条，等 AI 交付并验收通过再发下一条——同时发多条，AI 就会一次吐出整个项目，分层立刻失控。
模板不挑项目类型，网站、机器人、脚本、App、插件都能用。

---

## 模板 0 · 定规矩（每个新会话先发一次）

```
接下来我们按分层来推进，规则如下：
1. 分层只有五层：系统 → 子系统 → 模块 → 组件 → 接口。任何一段代码都要能说出它在哪一层。
2. 依赖只能从上层指向下层，不许出现循环依赖。
3. 先定接口（输入/输出/出错），后写实现；换实现时调用方不许改。
4. 一次只做一层，做完停下来等我确认，不要一次生成整个项目。
5. 不确定的地方直说"不确定"，不要编造仓库名、目录名、包名、版本号或模式名。
6. 别推荐超出我规模的方案（我不问就别提微服务、monorepo、消息队列、多智能体）。
7. 每个"完成"的声明都要贴出你实际运行的命令和原始输出，不要总结成"已通过"。
先回复"明白"，然后等我给需求。
```

## 模板 1 · 出图纸（先要方案，不要代码）

```
我要做的是：[一句话说清给谁用、帮他完成什么动作]。
他从哪里用：[网页 / 手机 / 聊天窗口 / 命令行 / 定时自动跑 / 没有界面]。
数据：[从哪来 / 要不要存 / 存下来给谁看 / 大概多少量]。
外部依赖：[要不要接平台接口、支付、地图、大模型等，没有就写"没有"]。
现状：[已有代码？必须用什么语言？跑在哪？谁维护？一个月最多花多少钱？]。

请只输出图纸，不要写代码：
1. 按 系统 → 子系统 → 模块 → 组件 → 接口 拆一遍，每层给名字 + 一句话职责 + 它不做什么。
2. 给一张依赖方向图（ASCII 就行），标明谁依赖谁。
3. 每个子系统说明：能不能单独替换？能不能单独测试？
4. 给数据模型草图：有哪些实体、谁写谁读、活多久。
5. 列出质量属性：多少人用、多快要能接受、数据敏感吗、每月成本上限。
6. 给一个目录树，标出每一层落在哪个目录。
7. 给两个不同的拆法候选，列出各自代价，然后推荐一个并说明理由。
8. 列出"现在不做什么"：这次明确不做的高复杂度方案，以及什么信号出现时才做。
9. 给落地顺序：先做什么、后做什么，每步怎么验证。
不许一次生成所有代码。
```

## 模板 2 · 定接口（在写任何实现之前）

```
现在只做 [模块名] 这一层的接口，不写实现。
请给出：
1. 这个模块对外承诺的能力清单（一句话一条）。
2. 每条能力的输入、输出、出错情况（用我这个语言里最常规的接口写法）。
3. 明确写出：哪些东西是它内部细节，外部不许碰。
4. 给一个"假实现"（直接返回固定值），让我能先验证调用方能不能跑通。
不要写真实业务逻辑。
```

---

## 模板 3 · 生成单个组件（一次一个文件）

```
请只实现 [组件名] 这一个文件，位置 [路径]。
要求：
- 严格遵守已经定好的接口 [接口名]，不许改接口签名；确实需要改就先告诉我为什么。
- 只依赖它下层的 [依赖项]，不许反向依赖上层。
- 不许引入新的第三方库；确实需要先说明理由等我同意。
- 交付时附带：这个文件属于哪一层、怎么单独验证它（命令或最小用例）。
不要顺手改动其他文件。
```

---

## 模板 4 · 复核分层（每完成一个模块就跑一次）

```
请以"架构审查员"的身份检查当前代码，只报告不修改：
1. 逐个文件标注它属于哪一层、哪个模块；有没有文件说不出归属？
2. 列出所有引用关系，指出是否存在循环依赖（给出环的具体路径）。
3. 有没有下层反过来依赖上层的地方？
4. 有没有绕过接口、直接访问别的模块内部的情况？
5. 有没有 utils / common 这类"什么都放"的目录在被当垃圾桶？
6. 密钥、路径、开关是不是散落在业务代码里（应该集中到配置）？
7. 同一张表/同一个数据是不是被两个模块写？
每条问题给出：位置、为什么算越界、最小修法。
```

---

## 模板 5 · 防跑偏口令（感觉 AI 又要一次性吐一大堆时）

```
停。你刚才一次给了太多东西，我没法验证。
请收回，只保留 [具体那一层/那一个文件] 的内容，其余先不要写。
并告诉我：这一步做完之后，我该用什么现象判断它是对的？
```

---

## 模板 6 · 该不该升级复杂度（决定要不要上重模式时）

```
我们现在是 [模块化单体 / 单智能体 / 单包] 的状态。
我想知道要不要升级到 [monorepo / 微服务 / 事件驱动 / CQRS / 消息队列 / 多智能体 / 云函数]。
请按这个格式回答，不要劝我上：
1. 这个模式的触发条件是什么？出处是哪（标准或官方文档，不要拿小众项目当依据）？
2. 我现在满足了哪几条、还差哪几条？
3. 如果上了，代价是什么（调试、一致性、工具链、成本）？
4. 什么信号出现时说明"现在该上了"？
5. 如果先不上，最短的那条演进路径是什么？
```

## 模板 7 · 接手别人的 / AI 生成的烂摊子

```
这是一份 [从哪来的] 代码，我看不懂，也不知道该从哪改。
请先不要改代码，只做诊断：
1. 画出它现在的模块和引用关系（ASCII 图）。
2. 按 系统 → 子系统 → 模块 → 组件 → 接口 标注每个文件，指出哪些文件无法归类。
3. 找出循环依赖、越界访问、以及一个文件干了多层事的地方。
4. 找出密钥硬编码、日志打印敏感信息、以及明显没跑过的代码。
5. 给出最小重构顺序：先动哪一个、为什么、改完怎么验证没坏。
6. 告诉我哪些地方先别动（动了风险大于收益）。
```

---

## 模板 8 · AI 代码验收（每批代码交付后发）

```
请对刚才这批代码做验收，逐条回答，不要替自己辩护：
1. 这次新增了哪些第三方依赖？逐个说明它真实存在（给出官方来源），以及为什么不用标准库。
2. 贴出你实际运行的命令和完整原始输出（不是"应该能跑"）。
3. 如果把你写的实现改坏一处，哪条测试会变红？贴出这条测试。
4. 这次有没有改动之前已经确认过的接口签名？如果有，为什么？
5. 有没有密钥、token、个人信息出现在代码或日志里？
6. 用大白话把这个文件干的事讲给我听，别用术语。
7. 这批代码里，哪个文件是"接手的人最容易看不懂"的？为什么必须存在这个复杂度？
```

## 模板 10 · 写代码前先定质量三道关（阶段 4–5 用）

```
在写实现之前，先把这三件事说清楚，别等出问题再说：
A. 失败设计
1. 这段代码会调用哪些外部东西（网络/数据库/文件/第三方）？每个的超时设多少？
2. 哪些操作可以重试？重试几次、怎么退避？哪些绝对不能重试？
3. 哪些写操作必须幂等（重复执行也不会出错）？幂等键用什么？
4. 依赖挂了的时候，用户看到什么？
B. 测试
1. 这段逻辑里，哪几条是业务规则（必须测）？
2. 用真实现还是假实现？假对象只在哪里用？
3. 哪条测试在"实现改坏"时一定会变红？
C. 安全与可读性
1. 这里的输入来自哪里？都校验了吗？
2. 有没有对象归属要校验（防越权）？
3. 有没有密钥、日志隐私、硬编码问题？
4. 命名能不能让人不看实现就懂？有没有看不懂的复杂度必须存在？
```

## 模板 11 · 性能与发布自查（阶段 6 用）

```
上线前请逐条回答，不要泛泛而谈：
A. 性能
1. 这条链路慢在哪一步？你测量过吗，数字是多少？
2. 数据库查询次数是多少？有没有 N+1？用到索引了吗？
3. 外部调用是串行还是并行？总耗时是各步骤之和吗？
4. 数据量涨 10 倍时，哪一步先崩？
5. 有没有缓存？失效策略是什么？会不会缓存到别人的数据？
B. 发布
1. 发布步骤能重复吗（脚本还是手敲）？
2. 回滚怎么做？演练过吗？
3. 数据库迁移幂等吗？迁移前备份能恢复吗？
4. 新功能有开关吗（出问题能不能不部署就关掉）？
5. 出事时谁会知道（告警还是等人发现）？
```

---

## 模板 9 · 补数据模型与质量属性（图纸阶段漏了就用这个）

```
图纸先放一下，我们把另外两样补上：
A. 数据
1. 有哪些实体？关键字段是什么？
2. 每个实体谁负责写、谁只能读？（一个实体只允许一个模块写）
3. 活多久？删除是软删还是硬删？备份和恢复怎么做？
4. 有没有金额、时间、并发写、重复提交这类容易出问题的地方？
B. 质量属性（请把"快""稳"换成数字）
1. 多少人用？峰值多少？
2. 出了故障能接受多久不能用？
3. 哪些数据敏感？会不会发给第三方（包括大模型）？
4. 每月成本上限多少？超了怎么降级？
5. 三个月后谁维护？他看不懂的话，我们该少写点什么？
每一条如果现在答不出来，就标"待确认"，不要编数字。
```
