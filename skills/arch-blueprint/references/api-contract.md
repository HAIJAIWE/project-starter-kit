# 接口与契约设计（信任边界就在这里）

契约有两种形态：**函数级**（同一进程内模块之间）和**网络级**（进程/系统之间）。
两者都要回答同一件事：**输入是什么、输出是什么、出错怎么办**。区别在于——网络级还要处理"对面可能根本不在"。

---

## 一、函数级契约

- 三件套写全：输入（类型 + 取值范围 + 可选性）、输出、**出错**（抛异常还是返回错误，全项目统一一种风格）。
- 不暴露内部类型：内部结构改了不该影响调用方。
- 可选参数要有明确默认值，别用"传空就代表…"这种隐式约定。
- 契约里不出现实现细节（连接、SQL、缓存键）。
- **内部模块之间也要有契约文件/类型定义**，而不是靠"看实现猜"。

## 二、信任边界：所有外部输入都要校验

不可信输入清单（**每一条都算外部**）：

| 来源 | 典型风险 |
|---|---|
| 用户表单 / URL 参数 / 请求体 | 越权、注入、超长、类型错 |
| 第三方接口响应 | 字段缺失、类型变了、返回 null、包含恶意内容 |
| 文件上传 / 本地文件 | 内容与扩展名不符、路径穿越、超大文件 |
| 环境变量 / 配置文件 | 缺失、空值、类型错（"false" 是字符串） |
| 消息队列 / webhook | 重复、乱序、伪造（要验签） |

规矩：
1. **在边界校验，进核心前收敛成干净类型。**
2. 白名单优先（只允许已知值），黑名单永远漏。
3. 校验失败给**可理解**的错误（哪个字段、为什么不行），不暴露内部结构。
4. 长度、数量、大小都要有上限（防超大请求拖垮服务）。

## 三、网络接口设计（HTTP 为例）

| 项 | 做法 |
|---|---|
| 资源命名 | 名词复数：`/orders`、`/orders/{id}`；动作交给方法 |
| 方法语义 | GET 安全且幂等；PUT 幂等；DELETE 幂等；POST 非幂等（要幂等就加幂等键） |
| 状态码 | 200 成功、201 创建、400 参数错、401 未认证、403 无权限、404 不存在、409 冲突、422 语义错、429 限流、500 服务错——**别一律 200** |
| 错误体 | 统一结构：`code`（稳定机器码）+ `message`（人话）+ `details`（字段级）；**不含堆栈/内部路径** |
| 分页 | 统一约定；优先游标（cursor）而非偏移（offset）；限制最大页大小 |
| 过滤/排序 | 白名单字段；别把查询语句直接暴露给客户端 |
| 时间 | UTC + 明确格式（ISO 8601） |
| 金额 | 整数最小单位（分）或十进制字符串，**不用浮点** |
| ID | 对外用不透明字符串（避免自增暴露业务量、便于换实现） |
| 限流 | 明确每接口配额，超限返回 429 + 重试提示 |

## 四、版本与兼容（改接口是最容易出事故的地方）

- **对外接口只加不改**：加字段安全，改语义/删字段危险。
- 破坏性变更要走新版本或新路径 + 过渡期（老客户端还在跑，尤其移动端/小程序无法强制升级）。
- 兼容策略：新增可选字段 → 双写/双读过渡 → 确认无旧调用方 → 再删旧字段。
- 接口下线要有时间表与通知（自己也要记在 CHANGELOG 里）。

## 五、幂等与重试安全（对外写法）

- 写接口支持幂等键：同键重复请求返回同一结果，不重复执行。
- 支付、下单、发消息、扣额度这几类**必须有**。
- GET 不许产生副作用（否则爬虫/预取都会误触发）。

## 六、契约文件（唯一真相）

- 用 **OpenAPI / JSON Schema / 语言类型定义**之一把契约写成文件，别只在文档里口述。
- 契约文件与实现**同时更新**；能用工具校验就用（生成客户端、请求校验、mock 服务）。
- 例：先写 schema → 生成假实现 → 调用方能跑 → 再填实现（对应 `roadmap.md` 阶段 3）。

## 七、接口评审清单

- [ ] 输入都有校验？范围/长度/必填都明确？
- [ ] 错误情况列全了吗（参数错、无权限、不存在、冲突、限流、内部错）？
- [ ] 状态码/错误码符合约定，且**稳定不变**（客户端要靠它）？
- [ ] 有没有泄露内部实现细节（堆栈、SQL、内部路径、版本号）？
- [ ] 分页/排序/过滤有上限吗？
- [ ] 写接口幂等吗？重复调用会怎样？
- [ ] 老客户端还能用吗（只加不改）？
- [ ] 契约文件更新了吗？与实现一致吗？
- [ ] 有没有鉴权？**每次访问对象都校验归属**（见 `security-checklist.md`）？
