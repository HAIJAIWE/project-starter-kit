# 验收：评分表、完成定义、常见坑

## 一、图纸评分表（出图纸后自己打一遍，别自我感觉良好）

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| **分层清晰** | 有文件说不出归属 | 能归属但个别含糊 | 任意文件都能说出层与模块 |
| **依赖无环** | 有环或未检查 | 检查过但跳级无理由 | 无环，跳级处都有理由 |
| **接口稳定** | 接口跟着实现改 | 有契约但掺了实现细节 | 契约清晰，换实现不改调用方 |
| **边界可测** | 子系统无法单独跑 | 部分可单独测 | 每个子系统都能单独替换+单独测试 |
| **工程基线** | 密钥在代码里、没 README | 缺 1–2 项必备 | 必备四项齐全（见 `engineering-baseline.md`） |

- **8–10 分**：可以开始落地。
- **5–7 分**：先把低分项补掉，再动手。
- **4 分及以下**：**不要写代码**，回 Step 1 重新澄清——这时的代码只会变成以后的包袱。

## 二、完成定义（DoD，缺一项都不算做完）

- [ ] 能一条命令启动（README 里写的就是实际用的）
- [ ] Step 2 的**第一条关键场景**真的手动走通了一遍
- [ ] 密钥不在代码、不在日志、不在前端产物里
- [ ] 至少有 1 条"改了实现就会失败"的测试，且真的跑过
- [ ] 出错时能看到原因（用户看到人话，日志能定位）
- [ ] 图纸与决策记录已落盘：`docs/architecture.md`、`docs/adr/`
- [ ] 明确知道怎么回滚到上一版

## 三、图纸验收清单（可与评分表并用）

- [ ] 五层各有明确落点
- [ ] 每个子系统写了**边界（不做什么）**，而不只是职责
- [ ] 依赖图无环；跨层跳级都写了理由
- [ ] 接口层没有任何实现逻辑
- [ ] 数据模型画了，且**没有两个子系统共写同一张表**
- [ ] 质量属性写成了数字（或明确标注"待确认 + 假设值"）
- [ ] 部署形态明确（跑在哪、怎么发布、怎么回滚）
- [ ] 给了两个候选拆法并说明为什么选这个
- [ ] 有一节「现在不做什么」，写清排除的重模式与启用信号
- [ ] 用户能用自己的话复述出这几个子系统（复述不出来 = 切错了）
- [ ] 所有引用都有出处，没有拿小众项目当标准

## 四、常见坑对照表

| 现象 | 真实原因 | 怎么办 |
|---|---|---|
| AI 一次生成 20 个文件，看不懂 | 没限制一次一层 | 用 `prompts.md` 模板 5 收回，按模板 3 一次一个文件 |
| 改一个功能崩三个地方 | 组件靠内部细节耦合 | 抽出接口，只通过契约通信 |
| 换个数据库/平台/大模型就要改核心 | 核心依赖了具体实现 | 外部依赖抽成接口，实现做适配器注册 |
| 接口老是跟着实现改 | 接口按实现写而非按调用方写 | 从调用方视角重写接口 |
| 业务逻辑散落在入口文件 | 只按技术分层，未按业务切 | 用垂直切片重排 |
| 小项目上了 monorepo 后整天折腾配置 | 复杂度提前引入 | 退回单包分层，等真有第二个要独立发布的包再拆 |
| EDA 后"数据不知何时一致" | 没提前评估 EDA 代价 | 补幂等 + outbox；关键路径退回同步调用 |
| 空目录凑层数，改起来更慢 | 做了样子工程 | 小项目允许省略目录 |
| 上线后才发现要加鉴权/队列 | 质量属性没在图纸阶段写 | 补 `data-and-quality.md` 那三问，重排一次 |
| 数据"删了"还能查到 | 软删没做过滤 / 没定留存规则 | 明确删除语义与留存期限 |
| 不知道 AI 写的到底跑没跑 | 把"已完成"当结论 | 按 `ai-code-acceptance.md` 要求贴原始输出 |

> AI 生成代码的八类专属问题（幻觉依赖、假测试、密钥泄漏等）见 `ai-code-acceptance.md`，不在此重复。

## 四·补、代码质量门（阶段 5 的出口，缺一项不算做完）

图纸对不代表代码对。每批代码交付时过一遍这五道门：

| 门 | 检查什么 | 参考 |
|---|---|---|
| **契约门** | 外部输入都校验了？错误情况列全了？接口没泄露内部细节？ | `api-contract.md` |
| **失败门** | 所有跨进程调用有超时？只重试幂等操作？关键写操作有幂等键？没有空 catch？ | `failure-design.md` |
| **测试门** | 业务规则有测试？那条"改了实现会变红"的测试存在？bug 修完补了回归测试？ | `testing-strategy.md` |
| **安全门** | 对象访问校验归属？查询参数化？密钥不在代码/日志/前端？ | `security-checklist.md` |
| **可读门** | 命名能看懂？没有看不懂但能跑的代码？没有硬编码与调试残留？ | `code-craft.md` |

通过标准：**"跑得起来 + 改得动 + 说得清"**，不是"AI 说完成了"。

## 五、什么时候才该升级复杂度（信号，不是时间表）

| 升级动作 | 出现的信号 |
|---|---|
| 拆出第一个独立子系统 | 有一大块能被单独替换或单独部署，且改动经常只碰它 |
| 用垂直切片重排 | 改一个业务功能要同时动 4 个以上技术分层目录 |
| 上 monorepo | 有 ≥3 个包需要独立发布，且确实要互相共享代码 |
| 引入事件驱动 / 消息队列 | 多个消费者要响应同一件事，或需要削峰、跨系统解耦 |
| 引入 CQRS | 读写负载或数据模型差异极大，且已到性能瓶颈 |
| 拆分微服务 | 多团队要独立发布与扩容，且已有分布式运维能力 |
| 上多智能体编排 | 单智能体 + 工具已无法覆盖，且任务步骤事先不可预知 |

**没有信号就不要升级。** 复杂度是借来的，利息用调试时间和稳定性还。
