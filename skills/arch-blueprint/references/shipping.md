# 落地：从"能跑"到"真在用"

**先对齐定义**。什么叫落地？三个条件同时满足才算：

1. **真有人在用**（不是只有你自己点过一次）；
2. **能改**（加功能不用重写，改坏了能回退）；
3. **出事能救**（数据能恢复、故障能定位、能回滚）。

只满足 1 叫"能演示"；满足 1+2 叫"能自用"。**别把"能演示"当"落地"。**

---

## 一、把图纸变成里程碑（里程碑才是落地的骨架）

图纸是最终形态；落地要按**里程碑**推进，每个里程碑都有一个**能给外人看的东西**：

| 里程碑 | 目标 | 出口标准（能验收） | 典型量级 |
|---|---|---|---|
| **M1 能演示** | 第一条关键场景走通，数据可以是假的 | 你能当着别人面点一遍，不崩 | 1–3 天 |
| **M2 能自用** | 真数据 + 真存储 + 基本错误处理；自己天天用 | 连续用 3 天没丢数据 | 1–3 周 |
| **M3 能给别人用** | 别人不用你在旁边也能用：引导、错误提示、权限 | 找一个真人（**不是你**）独立成功用一次 | 1–4 周 |
| **M4 能上线** | 监控 / 备份 / 回滚 / 条款齐备；出事能救 | 完成定义全过 + **回滚演练过** | 按需 |

**规矩**：

- M1 之前不写任何"以后会用得上"的功能；
- 每个里程碑结束时**要么上线、要么砍掉**——不要挂着半成品；
- 里程碑是**承诺**：写下来才知道自己有没有跑偏。

---

## 二、一次一个"可交付切片"（不是一次一层）

八阶段的"一次一层"是**架构层面**的推进顺序；到落地阶段要改成**纵向切片**：

1. 选一条关键场景 →
2. 从入口到存储**用假数据打通**（先能看到完整链路）→
3. 换成真逻辑 →
4. 补错误处理与失败路径 →
5. 补一条测试 →
6. 交给一个真人试。

**为什么**：横向开发（"先把所有接口/所有表写完"）会让你几周看不到能用的东西，也无法验证设计对不对。**能演示 > 能编译。**

---

## 三、联调与验收（落地的两个最大卡点）

**联调清单**——每个外部依赖都要过一遍：

- [ ] 超时与重试：对方慢/挂时你怎么反应
- [ ] 限流与配额：超限时返回什么、你怎么退避
- [ ] 错误码含义：哪些可重试、哪些必须人工
- [ ] 沙箱与生产的差异（数据、额度、行为）
- [ ] 回调验签与重复投递（webhook 类）
- [ ] 额度与计费：单价、免费额度、超限后果
- [ ] 对方的维护窗口与公告渠道（改版会让你静默失败）

**验收（UAT）**：

- 验收标准**写在前面**：谁 / 在什么条件下 / 做什么 / 看到什么算通过；
- 找**不是你的人**按清单点一遍；
- 把"没通过"当成信息，不是挫折——**这是唯一能发现"我以为能用"的办法**。

---

## 四、上线资源与合规清单（最容易卡在这一步）

**这些都有等待期，要在 M1 之后就动手申请**：

- [ ] 域名 + HTTPS 证书（中国大陆还要 **ICP 备案**，通常数周）
- [ ] 服务器 / 托管账号（付款方式、发票）
- [ ] 邮箱 / 短信 / 推送额度（多数要实名或企业资质）
- [ ] 第三方 API 额度（地图、大模型、支付：多需实名或资质）
- [ ] 支付资质（若收费：主体、结算账户、退款流程）
- [ ] 应用商店 / 小程序账号与审核周期（材料与规则）
- [ ] **隐私政策 + 用户协议**（只要收集任何个人信息就需要）
- [ ] 数据合规（收集范围、留存期限、删除机制、是否出境）
- [ ] 备份存储位置（与主库**分离**）

**纪律**：把这张表当任务清单提前跑——**它们的等待期经常比开发时间还长**，这是"项目卡在半成品"最高频的原因。

---

## 五、上线后怎么运营（落地不是终点）

| 事项 | 最小做法 |
|---|---|
| 监控 / 告警 | 服务不可用、错误率、备份失败 → **主动通知你**，不是等人发现 |
| 备份与恢复 | 每天自动备份 + **每季度真恢复一次**（只备份不演练 = 没备份） |
| 反馈渠道 | 一个用户能找到的入口（群 / 邮箱 / 表单），否则你不知道坏在哪 |
| 版本节奏 | 固定节奏发版（如每周）+ CHANGELOG；小步比大爆炸安全 |
| 事故处理 | 先止血（回滚 / 降级）→ 再定位 → 后复盘；复盘只问"哪一步能更早发现" |
| 技术债 | 一条台账：欠了什么、影响谁、什么时候还 |

## 六、"半成品"的七个典型原因（对照自查）

1. **只有最终形态，没有里程碑** → 永远"还差得远"；
2. **横向开发**（先写完全部接口 / 全部表） → 长期看不到能用东西；
3. **外部依赖没提前申请**（域名 / 资质 / 额度） → 卡在最后一步；
4. **验收标准没写在前面** → 永远"再改改"；
5. **范围一直在长**（每冒一个想法就重排） → 用"不做清单"挡住；
6. **没有回滚能力** → 不敢上线；
7. **上线后没人管**（无监控、无反馈渠道） → 悄悄坏掉。

---

## 七、落地检查清单（M4 之前逐条过）

- [ ] 第一条关键场景能演示（M1）
- [ ] 真数据 + 真存储，自用三天无丢失（M2）
- [ ] **一个真人（不是你）独立用成功**（M3）
- [ ] 密钥不在代码 / 日志 / 前端；日志不含隐私
- [ ] 备份存在，且**恢复演练过**
- [ ] 回滚步骤写过，且演练过
- [ ] 失败会主动告警
- [ ] 上线资源与合规项全部就位（含隐私政策 / 条款）
- [ ] README、部署说明、CHANGELOG 齐全（换个人也能跑起来）
- [ ] 验收标准与"这次不做"清单还在（防范围膨胀）

---

## 八、和八阶段的关系

落地不是第九个阶段，而是**阶段 4（工程化）→ 5（实现）→ 6（交付）的推进方式**：

- 阶段 4 负责"能不能改、能不能救"（工程基线 + 环境可复现）；
- 阶段 5 负责"一次一个可交付切片"（本文第二节）；
- 阶段 6 负责"上线资源 + 运营 + 事故处理"（本文第四、五节）。

**出口标准只有一个**：真人真用，且出事能救。
