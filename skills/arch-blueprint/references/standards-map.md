# 世界公认的是什么（权威锚点清单）

**一句话**：公认的不是"分几层"，而是——**协议守标准、依赖单向无环、边界按业务划、决策留痕、质量属性量化。**
层级命名（五层 / 四层 / 三层）**永远各说各的**，别去背它。

---

## 一、四个层次的"公认程度"完全不同（最容易混的地方）

| 层次 | 公认程度 | 违反了会怎样 | 例子 |
|---|---|---|---|
| **1 协议 / 国际标准** | **硬标准**，必须守 | 不能互通 / 不合规 | HTTP、SQL、TLS、OAuth 2.0、JSON、OpenAPI、ISO/IEC 42010、ISO/IEC 25010、WCAG |
| **2 设计原则** | 多体系收敛出的共识 | 现实会惩罚你（改不动、测不了） | 依赖单向、禁止循环、高内聚低耦合、关注点分离、信息隐藏、稳定依赖 |
| **3 表达与实践（事实标准）** | 广泛采用，**但不强制** | 别人看不懂 / 交接断档 | C4（画图）、ADR（记决策）、arc42（文档模板）、DDD 限界上下文（划边界）、语义化版本、测试金字塔、12-Factor |
| **4 架构模式** | ⚠️ **不是标准** | 复杂度反噬 | 分层、六边形、模块化单体、微服务、EDA、CQRS、事件溯源、微内核 |

**最容易犯的错**：把第 4 层（模式）当成第 1 层（标准）来遵守——"微服务是标准做法"是错的，它是**有触发条件与代价的选项**（ThoughtWorks 技术雷达多年未把微服务放进 Adopt 环）。

---

## 二、真正"没人反对"的只有两条

1. **高内聚、低耦合**（自 Parnas 1972 的信息隐藏起就是共识）
2. **不允许循环依赖**（无环依赖原则 ADP）

任何流派都不反对这两条；**其余都可以争论**。所以评审时最硬的两条依据就是它们。

---

## 三、按维度的权威锚点（要下结论时查这里）

| 你要决定 | 公认参照 | 性质 |
|---|---|---|
| 依赖方向 | Clean Architecture 的依赖规则 + 稳定依赖原则（SDP） | 原则、经典文献 |
| 边界怎么划 | DDD 的**限界上下文** | 事实标准 |
| 架构怎么描述 | **ISO/IEC 42010**（应包含哪些视角/关注点）+ **arc42**（模板） | 国际标准 + 事实标准 |
| 架构怎么画 | **C4 model** | 事实标准 |
| 决策怎么留 | **ADR**（Architecture Decision Record） | 事实标准 |
| 质量属性 | **ISO/IEC 25010** + 质量属性场景（SEI / ATAM） | 国际标准 + 评估方法 |
| 接口与协议 | HTTP / REST 语义、**OpenAPI**、JSON Schema | 硬标准 |
| 安全 | **OWASP Top 10 / ASVS** | 被监管广泛引用 |
| 无障碍 | **WCAG**（W3C） | 正式标准（被法规引用） |
| 部署与运维 | **12-Factor App** | 事实标准 |
| 版本与变更 | **语义化版本**、Conventional Commits、CHANGELOG | 事实标准 |
| 测试 | **测试金字塔**（Mike Cohn） | 事实标准 |
| 演进 | **Strangler Fig**、MonolithFirst | 经典实践 |
| 智能体编排 | Microsoft **AutoGen / Magentic-One** 文档 | 官方文档 |

## 四、引用纪律（与 `SKILL.md` 第五节的出处要求一致）

- **第 1、2 层**：可以直接当依据引用（"违反依赖规则"、"不符合 WCAG"）。
- **第 3 层**：说"**业界普遍做法**"，别说"标准要求"。
- **第 4 层**：只能说"**某模式适用于某条件**"，并且**必须同时给代价与触发条件**；禁止把它包装成"标准 / 最佳实践"。
- **具体开源项目**：只作对照，且要说明"这是某一家的做法"。

---

## 五、所以"别人做项目也是这样吗"的正确答法

- 成熟团队守的是 **1 + 2 层**（协议与原则），用 **3 层**（C4 画图 / ADR 记决策 / arc42 写文档）表达，**按信号**才引入 **4 层**；
- 业余项目通常三层都不显式做，靠约定撑着，改不动了才回头拆——这就是"越大越乱"的来源；
- 所以差别不是"知不知道更多模式"，而是**"有没有人守边界、有没有人留决策、有没有人量化质量"**。
