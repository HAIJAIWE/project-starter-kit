# 架构评审清单（依赖方向 · 适应度函数 · 问题清单）

评审的输出是**问题清单**，不是"我觉得还行"。只报告，不擅自改。

---

## 一、依赖方向检查

### 正确方向（端口—适配器 / 分层）
```
界面/接入 → 应用/业务 → 领域 → 接口（端口）
                              ↑（依赖倒置）
                        基础设施/适配器实现
```
**核心**：领域与业务**不依赖**框架、数据库、网络细节；外部实现依赖内部接口，而不是反过来。

### 危险信号（看到就是问题）
- 领域/业务层 import 了框架包（Spring、Django、Express 等）或数据库驱动。
- 基础设施细节泄漏到对外响应里（数据库 ID 格式、自增主键、内部错误堆栈、SQL 片段）。
- 两个模块互相引用（循环依赖）；服务之间同步调用链 > 3 层。
- 多个服务/模块直接读写同一张表（**两个模块共写同一张表** → 边界是假的）。
- 界面层直接访问存储层（跨层跳级，且没有写理由）。

### 怎么检查（**别用不存在的脚本**）
原提示词里的 `check_circular_deps.py` 与 `grep -r "import.*infrastructure"` 有两个问题：脚本不存在、且 grep 写法在 Windows 与多层目录下不可靠。用真实工具：

| 语言/生态 | 循环依赖 | 分层契约（把规则写成断言） |
|---|---|---|
| JS / TS | `madge --circular`、`dependency-cruiser` | `dependency-cruiser` 规则 |
| Python | `pydeps` | `import-linter`（分层契约可写进配置） |
| Java / Kotlin | `jdeps` | `ArchUnit` |
| Go | `go list -deps` | `go-arch-lint` |
| C# | 依赖分析器 | `NetArchTest` |
| Rust | `cargo modules` | `cargo-deny` |

**没有工具也要能查**：列出所有"谁引了谁"→ 画箭头图 → 能走回起点就是环 → 环上最稳定的概念下沉为接口。

## 二、架构适应度函数（把架构规则变成 CI 断言）

思路（ThoughtWorks 的 *fitness function* 概念）：**能被自动检查的架构规则，才不会被慢慢破坏。**

| 适应度函数 | 检查什么 | 什么时候跑 |
|---|---|---|
| 无循环依赖 | 依赖图无环 | 每次提交 |
| 分层不越界 | 领域层不依赖框架/基础设施 | 每次提交 |
| 接口兼容性 | 对外契约只加不改（对比基线） | 每次提交 |
| 模块体积 | 单模块文件数/行数不越界（防止上帝模块） | 每周 |
| 性能预算 | 首屏时间、接口 P95、包体积不超预算 | 每次发布 |
| 依赖健康 | 无已知高危漏洞、无停止维护的依赖 | 每周 |
| 决策覆盖率 | 单向门决策都有 ADR | 每月 |

**纪律**：适应度函数失败要**阻塞合并**；写在文档里但没人跑的规则，等于没有。

## 三、架构评审问题清单（逐条问，不问就漏）

**边界与领域**
1. 限界上下文是怎么划的？依据是业务能力、数据归属，还是"技术方便"？
2. 每个聚合的不变量是什么？谁能改它？
3. 有没有两个模块写同一份数据？
4. 术语在不同模块里含义一致吗（同一词不同义会撕开边界）？

**依赖与耦合**
5. 依赖方向单向吗？跨层跳级处有理由吗？
6. 换掉数据库/云/模型供应商要改多少处？
7. 有没有为了让"图好看"而存在的抽象？

**一致性与失败**
8. 一致性要求是什么？哪里可以最终一致？
9. 某个依赖挂掉时，用户看到什么？（降级方案）
10. 重试安全吗（幂等）？超时都设了吗？
11. 部分失败怎么上报？

**数据**
12. 数据量级与增长速度？一年后多少？
13. 金额与时区怎么存的？
14. 删除语义（软删/硬删）与留存期限？
15. 备份能恢复吗（演练过没有）？

**质量属性与成本**
16. 质量属性有数字吗（并发、P95、可用时长、月成本上限）？
17. 成本随规模怎么涨？有没有失控点（大模型调用、短信、带宽）？
18. 性能瓶颈在哪一步？测量过吗？

**演进与组织**
19. 什么信号出现时该升级？升级路径是什么？
20. 三个月后谁维护？他看得懂吗（可维护性是第一约束）？

**安全（快速过）**
21. 每次对象访问都校验归属吗（越权）？
22. 密钥在哪？日志里有没有隐私？

## 四、评审输出格式（固定四列，便于逐条处理）

| 位置 | 问题（为什么算问题） | 最小修法 | 严重度 |
|---|---|---|---|
| `src/order/service` | 领域层直接 import 了 ORM → 换库要改业务代码，且无法单测 | 抽 `OrderRepository` 接口，ORM 实现放适配器 | 高 |
| `api/response` | 返回了自增主键 → 暴露业务量、换存储格式会破坏客户端 | 对外改用不透明 ID | 中 |

严重度定义：
- **高**：会导致数据错误、安全问题、无法回滚，或让后续需求无法实现。
- **中**：会显著增加维护成本或返工量。
- **低**：可读性/一致性问题，不影响正确性。

**评审纪律**：只报告不擅自改；每条必须给出"最小修法"（不是"重构整个模块"）；对不确定的结论标明"需要验证"。

## 五、怎么抽样（不可能读完所有文件）

评审的第一难题是**范围**：几百个文件读不完。按这六条挑，性价比最高：

| 从哪下手 | 为什么 |
|---|---|
| **从入口往下** | 入口 → 它调用的第一层 → 关键分支（主链路最快暴露结构问题） |
| **从数据往上** | 表结构 / 迁移脚本 → 谁写它 → 谁读它（数据归属决定边界真假） |
| **从 diff 看** | 最近改动的文件优先（缺陷集中在**新代码**与**新旧交界**） |
| **从名字找嫌疑** | `utils` / `common` / `helper` / `manager`（名字含糊处往往职责也含糊） |
| **从配置与密钥找** | `.env`、日志、前端产物（安全与隐私问题多在这一带） |
| **从测试看结构** | 测试文件告诉你作者的意图与哪些地方"不敢测" |

**覆盖下限**（少于这些，不要声称"评审过"）：入口 + 数据访问 + 认证/权限 + **一条完整业务链路**。
**必须写明没读的部分**——这比假装读完专业得多。

## 六、体检报告模板（可直接复制）

```markdown
# <项目/模块> 技术体检报告
日期 / 范围（文件与行数）/ 抽样方式 / **未覆盖**

## 一、结论（先给判断）
- 能不能放行：可以 / 有条件可以 / 不放行
- 一句话理由：

## 二、风险清单
| # | 位置(文件:行) | 问题（类别） | 触发条件 | 影响 | 最小修法 | 严重度 | 状态 |
|---|---|---|---|---|---|---|---|
| 1 | | | | | | 高/中/低 | 已复现 / 设计风险 / 材料缺口 |

## 三、已复现的问题（有反例或可执行证据）
## 四、设计风险（触发条件明确，但未构造出复现）
## 五、材料缺口（缺什么资料导致无法判断）
## 六、放行条件（阻断项 + 排期项）
## 七、正面发现（这段代码做强的地方）
## 八、建议的下一步（按优先级，含验证方式）
```

**三条硬规矩**：① 每条风险必须有 `文件:行`；② **没跑过的检查只能列为计划**，不能写成"已验证"；③ 区分"已复现 / 设计风险 / 材料缺口"，不要把猜测写成结论。
