# ADR 模板与写法

架构决策记录（**ADR**，Architecture Decision Record；概念出自 Michael Nygard）记录的是**为什么**这么选，不是"设计长什么样"。目的是：三个月后（或换人接手时）不用把已经吵过的架再吵一遍。

---

## 一、什么时候该写 ADR

| 该写 | 不必写 |
|---|---|
| 单向门决策：数据库、部署平台、外部供应商、核心框架、对外接口格式 | 双向门：格式化工具、日志库、目录名 |
| 跨模块/跨系统的边界划分 | 单个函数怎么实现 |
| 会被反复推翻的决策（不写就会有人反复提） | 一次性的临时开关 |
| 有明确代价、且以后可能重新评估的决策 | 无争议的显然选择 |

**数量级参考**：一个小项目 3–8 条就够；每条 5 分钟。

## 二、存放与命名

- 位置：`docs/adr/`
- 命名：`0001-选型-数据库.md`、`0002-边界-订单与库存.md`（编号递增，**永不重排**）
- 状态流转：提议中 → 已接受 → （被 ADR-000X 取代 / 已弃用）
- **不要修改已接受的 ADR**：改变主意就写新的一条，并标注它取代了谁（历史本身就是价值）

## 三、模板

```markdown
# ADR-0001: [决策标题]

## 状态
提议中 | 已接受 | 已弃用 | 被 ADR-XXXX 取代

## 日期与决策人
[YYYY-MM-DD] / [谁]

## 背景（为什么现在必须决定）
是什么问题、什么约束促使我们做这个决策？
硬约束写在这里：语言/平台/预算/合规/人力/已有代码。

## 决策
我们决定做什么？（一句话能说清）
如果不做任何决定，默认会发生什么？

## 备选方案与代价
| 方案 | 优点 | 代价（放弃了什么） | 是否选用 |
|---|---|---|---|
| A | | | |
| B | | | |

## 影响（后果）
- 让什么变得更容易：
- 让什么变得更难：
- 引入了什么新的风险：
- 依赖这个决策的其他决策：

## 重新评估的信号
什么情况出现时，我们应该回头改这个决策？
（例：日活超过 X / 单表超过 Y 行 / 供应商涨价超过 Z%）

## 备注
相关链接、原型结论、参考出处（标准或官方文档优先）
```

## 四、常见写错的写法

| 错误写法 | 为什么错 | 改法 |
|---|---|---|
| 只写"我们用了 PostgreSQL" | 这是"是什么"，不是"为什么" | 写清候选、判断标准、放弃的代价 |
| 没有"重新评估的信号" | 决策变成永久，没人敢动 | 补一行信号 |
| 备选方案只写一个 | 等于没做选择 | 至少两个，并写清各自代价 |
| 把设计图塞进 ADR | 混淆设计与决策 | 图放架构文档，ADR 只记决策 |
| 决策后偷偷改实现 | 记录与事实脱节 | 实现偏离就写新 ADR |
| 引用"某网红项目这么做的" | 无法核实、会误导 | 引用标准/官方文档；项目只作对照并说明性质 |

## 五、给 AI 用的提示词片段

```
请把刚才这个决策写成 ADR，放在 docs/adr/，编号递增：
必须包含：状态、背景（含硬约束）、决策、至少两个备选方案及各自代价、
影响（更容易/更难/新风险）、重新评估的信号。
不许写"是什么"当"为什么"；引用要给出来源；不确定的地方标"待确认"。
```
